# Karpathy Guidelines (카파시 가이드라인)

Andrej Karpathy가 관찰한 [LLM 코딩 함정](https://x.com/karpathy/status/2015883857489522876)을 기반으로, LLM이 자주 저지르는 코딩 실수를 줄이는 행동 규칙이다. **클로드가 무리해서 코드를 짜다가 멀쩡한 부분까지 깨뜨리는 것을 방지한다.**

**Tradeoff:** 이 가이드라인은 속도보다 신중함에 무게를 둔다. 사소한 작업은 판단에 맡겨라.

## 1. Think Before Coding (코딩 전에 생각하라)

**추측하지 마라. 혼란을 숨기지 마라. 트레이드오프를 드러내라.**

구현 전:
- 가정을 명시적으로 말하라. 불확실하면 질문하라.
- 해석이 여러 갈래면 모두 제시하라 — 혼자 조용히 하나를 고르지 마라.
- 더 단순한 방법이 있으면 말하라. 합당하면 반대 의견을 내라.
- 불명확한 게 있으면 멈춰라. 무엇이 헷갈리는지 이름 붙이고 질문하라.

## 2. Simplicity First (단순함 우선)

**문제를 푸는 최소한의 코드만. 추측성 작업 금지.**

- 요청받지 않은 기능은 만들지 마라.
- 한 번만 쓰는 코드에 추상화를 만들지 마라.
- 요청하지 않은 "유연성"이나 "설정 가능성"을 넣지 마라.
- 일어날 수 없는 시나리오에 대한 에러 처리를 넣지 마라.
- 200줄을 짰는데 50줄로 가능하면, 다시 써라.

스스로에게 물어라: "시니어 엔지니어가 이걸 보면 과하다고 할까?" 그렇다면 단순화하라.

## 3. Surgical Changes (최소 변경)

**꼭 필요한 곳만 건드려라. 네가 만든 흔적만 정리하라.**

기존 코드를 수정할 때:
- 인접한 코드, 주석, 포맷을 "개선"하지 마라.
- 망가지지 않은 것을 리팩터링하지 마라.
- 다르게 하고 싶더라도 기존 스타일을 따라라.
- 관련 없는 죽은 코드를 발견하면 — 삭제하지 말고 언급만 하라.

네 변경이 고아(orphan)를 만들면:
- 네 변경 때문에 안 쓰이게 된 import/변수/함수는 제거하라.
- 요청받지 않은 한, 원래 있던 죽은 코드는 제거하지 마라.

테스트: 변경된 모든 줄이 사용자의 요청으로 직접 추적되어야 한다.

## 4. Goal-Driven Execution (목표 기반 실행)

**성공 기준을 정의하라. 검증될 때까지 반복하라.**

작업을 검증 가능한 목표로 바꿔라:
- "검증 추가" → "잘못된 입력에 대한 테스트를 쓰고, 통과시켜라"
- "버그 수정" → "버그를 재현하는 테스트를 쓰고, 통과시켜라"
- "X 리팩터링" → "전후 테스트가 통과하는지 확인하라"

여러 단계 작업은 간단한 계획을 명시하라:
```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

강한 성공 기준은 독립적으로 반복(loop)하게 해준다. 약한 기준("동작하게 해줘")은 끊임없는 재확인을 요구한다.

## 적용 신호 (When this applies)

- 새 코드 작성, 기존 코드 수정, 리팩터링, 버그 수정 — 사실상 모든 코드 작업.
- 다른 표준 스킬과 함께 항상 켜두는 "always-on" 가이드라인으로 동작한다.
- [[superpowers-workflow]]의 구현 단계와 자연스럽게 결합된다 — Superpowers가 *언제* 무엇을 할지(프로세스)를 정하면, Karpathy가 *어떻게* 안전하게 짤지(품질)를 정한다.
