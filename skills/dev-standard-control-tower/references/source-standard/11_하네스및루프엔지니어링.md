# UDS-111 하네스 및 루프 엔지니어링 표준

버전: 1.0.0 | 상태: 검토초안 | 소유자: AI팀 기술책임자

## 1. 목적

본 표준은 프로젝트의 성격과 위험에 따라 일반 개발, 하네스 엔지니어링 또는 하네스 기반 루프 엔지니어링을 선택하고, AI·자동화·핵심 엔진이 승인된 입력과 도구 안에서 재현 가능하고 중단 가능한 방식으로 실행되도록 설계·검증하는 기준을 정의한다.

하네스는 모델이나 에이전트 자체가 아니다. 입력 계약, 도구, 상태, 검증기, 실행 한도, 승인 지점, 로그와 복구 절차를 묶어 실행을 통제하는 소프트웨어 경계다.

## 2. 용어

| 용어 | 정의 |
|---|---|
| 하네스 | 실행 대상을 둘러싸고 입력, 도구, 상태, 검증, 제한, 기록과 복구를 통제하는 실행 프레임 |
| 작업자 | 하네스 안에서 실제 작업을 수행하는 함수, 서비스, 모델 또는 에이전트 |
| 검증기 | 결과의 형식, 규칙, 근거, 안전성과 완료조건을 판정하는 결정론적 구성요소 |
| 단일 패스 | 입력을 한 번 처리하고 검증한 뒤 종료하는 실행 방식 |
| 제한 루프 | 검증 실패 또는 미완료 상태에서 정해진 횟수만 보완하는 반복 방식 |
| 장기 루프 | 체크포인트를 유지하며 여러 단계 또는 장시간 실행하는 방식 |
| 상태 | 실행 단계, 입력 버전, 중간 산출물, 오류, 승인과 재시도 정보를 포함한 명시적 데이터 |
| 체크포인트 | 중단 후 안전하게 재개할 수 있도록 저장한 일관된 실행 상태 |
| 종료조건 | 성공, 실패, 한도 초과, 인간 승인 대기 등 루프를 끝내는 기계 판정 기준 |
| 킬 스위치 | 운영자가 신규 실행과 진행 중 실행을 즉시 중지하는 통제 |

## 3. 개발기법 분류

### 3.1 T0 일반 개발

결정론적 코드와 명확한 입력·출력만으로 해결되며 AI 또는 반복 자동화가 필요 없는 경우다.

예:

- 일반 CRUD
- 정해진 계산식
- 단순 데이터 변환
- 명확한 API 연계

T0에서도 테스트, 예외 처리, 관측과 롤백 기준은 적용한다.

### 3.2 T1 하네스 엔지니어링

한 번의 실행이라도 외부 도구, AI 모델, 복잡한 파이프라인 또는 실패 가능성이 있는 자동화를 통제해야 하는 경우다.

예:

- 문서 분류·요약
- OCR 파이프라인
- 외부 API 조합
- 코드 생성 후 정적 검증
- 데이터 추출 후 스키마 검증

T1은 입력 계약과 출력 검증기를 갖춘 단일 패스를 기본으로 한다. 재시도는 동일 입력에 대한 기술적 실패처럼 안전한 경우에만 제한적으로 허용한다.

### 3.3 T2 하네스 기반 제한 루프 엔지니어링

초기 결과가 불완전할 수 있고 검증 결과를 이용해 보완해야 하지만, 목표와 반복 한도를 명확히 정할 수 있는 경우다.

예:

- 요구사항 기반 코드 작성→정적 검사→수정
- 문서 추출→필드 검증→누락 보완
- 검색→근거 평가→추가 검색
- 테스트 실패 분석→제한적 수정→재검증

반드시 하네스가 루프를 소유해야 한다. 작업자가 스스로 무제한 반복하거나 종료 여부를 단독 결정해서는 안 된다.

### 3.4 T3 하네스 기반 장기·운영 루프

여러 작업, 장시간 실행, 외부 상태 변화 또는 운영 자동화를 지속적으로 처리하는 경우다.

예:

- 승인 정책에 따른 운영 에이전트
- 장시간 분석·수집 작업
- 이벤트 기반 자동 복구
- 여러 전문 에이전트의 협업

T3는 기본적으로 L3 이상으로 취급하며, A3 권한 검토, 영속 상태, 체크포인트, 운영 대시보드, 킬 스위치, 복구 훈련과 독립 보안 검토가 필요하다.

## 4. 선택 기준

프로젝트 또는 기능 단위로 다음 질문을 평가한다.

| 판단 질문 | 아니오 | 예 |
|---|---|---|
| 출력이 규칙 기반 코드만으로 완전히 결정되는가? | T1 검토 | T0 우선 |
| 모델, 외부 도구 또는 불확실한 서비스 결과를 사용하는가? | T0 가능 | 최소 T1 |
| 결과의 형식·근거·품질 검증이 필요한가? | 일반 테스트 | 최소 T1 |
| 첫 결과가 실패하면 검증 피드백으로 보완할 가치가 있는가? | T1 | T2 검토 |
| 성공조건과 반복 한도를 기계적으로 판정할 수 있는가? | 루프 금지 | T2 가능 |
| 삭제·배포·결제·개인정보 전송 등 비가역 영향이 있는가? | 자동 실행 가능성 검토 | 인간 승인 필수 |
| 실행이 프로세스 재시작 이후에도 계속되어야 하는가? | 메모리 상태 가능 | T3 또는 영속 체크포인트 |
| 여러 에이전트가 같은 상태를 변경하는가? | 단일 작업자 | T3 수준 조정·락 필요 |

선택 원칙:

1. 요구를 충족하는 가장 단순한 기법을 선택한다.
2. 검증 가능한 단일 패스로 충분하면 루프를 도입하지 않는다.
3. 검증기가 없으면 루프를 도입하지 않는다.
4. 반복 횟수가 많을수록 품질이 자동으로 좋아진다고 가정하지 않는다.
5. T2·T3 선택은 개발기법 선정서에 근거와 대안을 기록하고 기술책임자가 승인한다.

### 4.1 표준 SKILL 선택

| 선정 등급 | 복사·적용할 표준 SKILL |
|---|---|
| T0 | 없음. 일반 개발 표준 적용 |
| T1 | `SKILL/harness-engineering-standard/` |
| T2 | `SKILL/harness-engineering-standard/` + `SKILL/harness-loop-engineering-standard/` |
| T3 | T2와 동일하며 루프 SKILL의 T3 운영 통제를 모두 적용 |

두 SKILL은 프로젝트에서 새로 작성하는 예시가 아니라 즉시 복사·사용하는 정본 실행 지침이다. 프로젝트별 하네스 설계서는 도구, 상태 저장소, 검증기, 한도와 승인 지점을 구체화하며 표준 SKILL의 안전 통제를 삭제하거나 완화할 수 없다.

## 5. 하네스 필수 구성

### 5.1 입력 계약

- 입력 스키마, 타입, 길이와 필수 여부
- 출처와 신뢰 수준
- 허용 파일·콘텐츠 유형
- 개인정보·기밀정보 분류
- 입력 버전과 중복 식별자
- 거부 조건과 사용자 오류 메시지

검증되지 않은 원문을 시스템 프롬프트, 명령 또는 도구 인자로 직접 사용하지 않는다.

### 5.2 실행 컨텍스트

실행마다 고유 실행 ID를 부여하고 다음을 고정한다.

- 요구사항·작업 ID
- 입력 버전과 해시
- 하네스·프롬프트·모델·도구 버전
- AI 권한 등급
- 호출자와 테넌트
- 시간·비용·토큰·자원 예산
- 허용 도구와 경로
- 데이터 분류와 보존 정책

### 5.3 도구 레지스트리

각 도구는 다음 계약을 갖는다.

| 항목 | 설명 |
|---|---|
| 도구 ID·버전 | 변경 추적 가능한 식별자 |
| 입력·출력 스키마 | 구조화된 계약 |
| 권한 | 읽기·쓰기·외부 전송 범위 |
| 시간 제한 | 호출 최대 시간 |
| 재시도 | 재시도 가능 오류와 최대 횟수 |
| 멱등성 | 중복 실행 시 영향 |
| 부작용 | 데이터 변경, 과금, 알림, 배포 |
| 보상 작업 | 실패 또는 취소 시 복구 |
| 감사 필드 | 호출자, 대상, 결과, 추적 ID |

도구는 허용목록 방식으로 등록한다. 모델이 임의의 명령, URL, 파일 경로 또는 SQL을 실행하게 하지 않는다.

### 5.4 상태 머신

상태를 문자열 로그가 아니라 구조화된 값으로 관리한다.

권장 기본 상태:

`CREATED → VALIDATED → PLANNED → RUNNING → VERIFYING → SUCCEEDED`

예외 상태:

`WAITING_APPROVAL`, `RETRYABLE_FAILED`, `FAILED`, `CANCELLED`, `LIMIT_EXCEEDED`, `ROLLING_BACK`, `ROLLED_BACK`

각 전이는 허용 조건, 수행 작업, 저장 데이터와 다음 상태를 명시한다.

### 5.5 검증기

검증기는 가능한 한 작업자와 분리하고 결정론적으로 구현한다.

검증 순서:

1. 구문·스키마
2. 필수값·형식·범위
3. 업무 규칙
4. 데이터 정합성
5. 출처·근거
6. 권한·보안
7. 품질 점수 또는 인수조건

LLM 자기평가만으로 성공을 판정하지 않는다. 의미 평가에 모델이 필요한 경우에도 스키마, 근거 존재, 수치와 금지조건은 코드로 검증한다.

### 5.6 관측과 증적

최소 기록:

- 실행 ID와 상관관계 ID
- 단계와 상태 전이
- 입력·출력의 안전한 식별자와 해시
- 도구 호출, 시간, 결과와 오류코드
- 모델·프롬프트·도구 버전
- 검증 결과와 실패 사유
- 반복 횟수와 누적 비용
- 인간 승인과 결정
- 취소·롤백·재개 이력

비밀번호, 토큰, 원문 개인정보와 불필요한 프롬프트 전문은 기록하지 않는다.

## 6. 루프 설계

### 6.1 표준 루프

```text
입력 검증
  → 계획 생성
  → 다음 단일 행동 선택
  → 정책·권한 검사
  → 도구 실행
  → 결과 구조화
  → 검증
  → 성공 / 보완 / 승인대기 / 실패 / 한도초과
```

한 반복에서 실행하는 행동 수를 제한한다. 계획 전체를 검증 없이 한 번에 실행하지 않는다.

### 6.2 루프 불변조건

모든 반복에서 다음이 참이어야 한다.

- 작업 목적과 요구사항 ID가 변하지 않는다.
- 허용 도구와 데이터 경계가 확대되지 않는다.
- 누적 비용과 반복 수가 감소하지 않고 정확히 기록된다.
- 완료된 단계의 증적이 보존된다.
- 입력과 출력 스키마가 유지된다.
- 인간 승인 항목을 우회하지 않는다.
- 다른 테넌트·고객·프로젝트 데이터가 섞이지 않는다.

### 6.3 종료조건

모든 루프는 시작 전에 다음 종료조건을 정의한다.

| 유형 | 예 |
|---|---|
| 성공 | 모든 필수 검증 통과 |
| 실패 | 복구 불가능 오류, 금지조건 위반 |
| 반복 한도 | 최대 단계 또는 동일 오류 3회 |
| 시간 한도 | 실행시간 또는 단계별 시간 초과 |
| 비용 한도 | 토큰, API 비용 또는 자원 예산 초과 |
| 품질 정체 | 연속 3회 품질 점수 개선 없음 |
| 승인 대기 | 비가역 작업 또는 정책 예외 |
| 사용자 취소 | 취소 요청 또는 킬 스위치 |

`완료된 것 같다`, 모델의 자연어 선언 또는 빈 작업목록만으로 성공 처리하지 않는다.

### 6.4 재시도와 보완

- 네트워크 시간 초과처럼 일시적 오류와 결과 품질 미달을 구분한다.
- 동일 입력의 기술적 재시도에는 지수 백오프와 지터를 적용한다.
- 품질 보완은 검증 실패 항목만 대상으로 한다.
- 동일 프롬프트·동일 도구·동일 입력의 무의미한 반복을 금지한다.
- 실패 원인이 권한, 입력 부족 또는 정책 위반이면 재시도하지 않는다.
- 부작용이 있는 도구는 멱등키 또는 실행 전 중복 검사를 사용한다.

### 6.5 인간 승인

다음 작업은 루프가 계획할 수 있으나 승인 전 실행하지 않는다.

- 운영 배포와 설정 변경
- 데이터 삭제·대량 수정·마이그레이션
- 외부 전송과 고객 통지
- 결제·구매·과금
- 권한 부여·회수
- 보안 통제 비활성화
- 요구사항·합격 기준 변경
- 고위험 업무의 최종 판단

승인 요청에는 작업, 대상, 예상 영향, 복구 방법, 관련 증적과 유효기간을 포함한다. 승인 내용과 다른 실행은 새 승인을 받아야 한다.

### 6.6 체크포인트와 재개

T2에서 여러 분 이상 실행되거나 T3인 경우 체크포인트를 둔다.

- 상태 변경과 산출물 저장을 일관되게 처리한다.
- 재개 시 입력, 코드, 프롬프트와 도구 버전 변화를 확인한다.
- 이미 완료된 부작용을 중복 실행하지 않는다.
- 호환되지 않는 버전이면 자동 재개하지 않고 마이그레이션 또는 인간 판단을 요청한다.

### 6.7 취소와 롤백

- 각 단계는 취소 가능 여부와 안전한 중단점을 정의한다.
- 취소 요청 후 신규 도구 호출을 시작하지 않는다.
- 진행 중 호출은 타임아웃 또는 취소 토큰으로 종료한다.
- 데이터 변경은 트랜잭션, 보상 작업 또는 전진 수정 방법을 준비한다.
- 롤백 실패는 원래 오류와 분리하여 보고한다.

## 8. 개발 절차

### 단계 1. 기법 선정

1. 기능을 결정론성, 불확실성, 반복 필요성, 부작용과 실행시간으로 평가한다.
2. T0~T3를 기능 단위로 선택한다.
3. 더 단순한 대안과 루프를 사용하지 않을 수 없는 이유를 기록한다.
4. L등급과 A등급을 조정한다.

### 단계 2. 계약과 위협 설계

1. 입력·출력 스키마
2. 도구 계약
3. 상태 머신
4. 검증기와 성공조건
5. 데이터 분류와 권한
6. 실패, 취소, 롤백과 재개
7. 프롬프트 인젝션, 도구 오용, 데이터 혼입과 비용 폭주 위협

### 단계 3. 결정론적 외피 구현

모델 호출보다 먼저 입력 검증, 정책, 도구 어댑터, 상태 저장, 검증기와 한도 계측을 구현한다.

### 단계 4. 작업자 연결

모델·에이전트·서비스는 구조화된 계약을 통해 연결한다. 자유 형식 텍스트를 실행 명령으로 직접 해석하지 않는다.

### 단계 5. 시나리오 검증

정상, 입력 오류, 도구 실패, 품질 미달, 반복 정체, 승인 대기, 취소, 재개, 롤백과 한도 초과를 검증한다.

### 단계 6. 관찰 모드

T3 또는 중요한 T2는 실제 변경 없이 제안과 판정만 기록하는 관찰·드라이런 모드를 거친다.

### 단계 7. 단계적 권한 확대

A1에서 시작하여 증적과 승인에 따라 A2, A3로 확대한다. 실패율, 비용 또는 안전 지표가 악화되면 즉시 이전 권한으로 낮춘다.

## 11. 운영 기준

최소 운영지표:

- 실행·성공·실패·취소 건수
- 단계별 지연시간
- 반복 횟수 분포
- 도구별 오류율
- 검증 실패 사유
- 인간 승인 대기시간
- 실행당 비용·토큰·자원
- 롤백과 수동 개입률

경보 예:

- 실패율 또는 비용 급증
- 동일 단계 반복 증가
- 승인 없이 부작용 도구 호출 시도
- 데이터 경계 위반
- 체크포인트 저장 실패
- 킬 스위치 또는 관측 기능 장애

모델, 프롬프트, 도구 또는 검증기 변경은 버전별 평가 후 단계적으로 적용한다. 전체 실행을 즉시 새 버전으로 전환하지 않는다.

## 12. 금지사항

- 검증기 없는 에이전틱 루프
- `while true` 형태의 무제한 반복
- 모델이 스스로 권한·도구·예산을 확대하는 구조
- 자연어 출력의 직접 SQL·쉘·배포 실행
- 외부 문서의 지시를 상위 명령으로 취급
- LLM 자기평가만으로 성공 판정
- 메모리 내 상태만 사용하는 장기 작업
- 승인 대기 중 자동 우회
- 테스트 환경과 운영의 데이터·도구 혼용
- 타 고객·타 프로젝트 산출물 혼입
- 오류를 숨기고 빈 결과를 성공 처리
- 실제 증적 없이 자율형·무인 운영 가능으로 보고
