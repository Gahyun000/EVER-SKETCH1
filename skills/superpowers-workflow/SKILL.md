# Superpowers Workflow (슈퍼파워)

코드부터 짜는 현상을 막는다. **요구사항 정리 → 구현 계획 → 테스트 → 구현 → 코드 리뷰**의 단계를 거치도록 강제하여, 버그를 줄이고 첫 구현의 품질을 대폭 끌어올린다.

이 스킬은 obra/superpowers의 전체 파이프라인을 조정하는 **경량 라우터**다. 세부 절차가 필요한 순간에는 이 저장소에 이식된 [[systematic-debugging]], [[test-driven-development]], [[verification-before-completion]], [[receiving-code-review]]를 각각 읽어 적용한다.

## 우선순위 규칙 (Instruction Priority)

1. **시스템·개발자·런타임 정책** — 항상 최우선
2. **사용자의 명시적 지시** (AGENTS.md, CLAUDE.md, 직접 요청)
3. **이 워크플로** — 위 지시와 충돌하지 않는 범위에서 적용

사용자가 "TDD 쓰지 마"라고 하면 사용자를 따른다. 사용자가 통제권을 갖는다.

## 핵심 규칙: 프로세스가 구현보다 먼저다

> "Let's build X" → 먼저 brainstorm(요구사항/설계), 그 다음 구현.
> "Fix this bug" → 먼저 체계적 디버깅, 그 다음 도메인 작업.

<HARD-GATE>
새 기능·새 컴포넌트·아키텍처 변경처럼 여러 해석이 가능한 창작 작업은 설계를 제시하고 사용자가 승인한 뒤 구현한다. 명백한 오타, 사용자가 이미 승인한 구체적 계획의 실행, 읽기 전용 조사, 긴급한 단일 결함 수정에는 이 게이트를 기계적으로 적용하지 않는다.
</HARD-GATE>

### 안티패턴: "이건 너무 단순해서 설계가 필요 없어"

작업의 위험과 모호성에 맞춰 절차의 무게를 조절한다. 작은 변경은 성공 조건 한 줄이면 충분할 수 있고, 제품 동작이나 데이터 모델이 바뀌면 명시적 설계 승인이 필요하다.

## 5단계 워크플로

각 단계를 todo 항목으로 만들고 순서대로 완료하라.

### 1단계 — 요구사항 정리 (Brainstorm)
- 먼저 프로젝트 컨텍스트를 탐색한다(파일, 문서, 최근 커밋).
- 질문은 **한 번에 하나씩**. 가능하면 객관식으로. 목적·제약·성공 기준을 이해한다.
- 규모가 크면(여러 독립 서브시스템) 먼저 분해를 제안한다. 각 서브프로젝트가 자체 spec → plan → 구현 사이클을 갖는다.
- 2~3개 접근법을 트레이드오프와 함께 제시하고, 추천안을 먼저 제시하며 이유를 설명한다.
- 설계를 섹션별로(복잡도에 맞춰) 제시하고, 섹션마다 승인을 받는다. 아키텍처·컴포넌트·데이터 흐름·에러 처리·테스트를 다룬다.
- 승인된 설계를 `docs/specs/YYYY-MM-DD-<topic>-design.md`에 기록한다.
- **Spec 자체 검토**: placeholder/모순/모호함/범위를 점검하고 인라인 수정.
- 사용자에게 작성된 spec 검토를 요청하고, 승인 후에만 진행한다.

### 2단계 — 구현 계획 (Plan)
- "의욕 넘치는 주니어 엔지니어도 따라올 만큼" 명확한 계획을 만든다.
- 작은 단위 작업으로 쪼개고, 각 작업에 **파일 경로 + 검증 단계**를 명시한다.
- YAGNI / DRY 원칙으로 불필요한 것을 제거한다.

### 3단계 — 테스트 먼저 (Test-Driven, 엄격)
- RED → GREEN → REFACTOR.
- [[test-driven-development]]를 읽고, 실패하는 테스트를 먼저 쓰고(RED), 통과시키는 최소 코드를 짜고(GREEN), 그 다음 정리한다(REFACTOR).
- TDD는 **엄격(rigid)** 스킬이다 — 규율을 적당히 풀지 마라.

### 4단계 — 구현 (Implement)
- 계획의 작업을 하나씩 처리한다. [[karpathy-guidelines]]를 적용하여 최소·수술적 변경을 한다.
- 큰 작업은 작업별 서브에이전트로 분배(subagent-driven)하고, 그 결과를 검수한다.
- 파일이 커지면 책임이 과한 신호다 — 분리를 고려한다.

### 5단계 — 코드 리뷰 (Review)
- 작업 사이사이에 **계획 대비** 코드 리뷰를 수행한다. 리뷰를 받았으면 [[receiving-code-review]]로 제안의 기술적 타당성을 먼저 검증한다.
- 완료 선언 전에 [[verification-before-completion]]을 읽고 새 증거를 수집한다.
- "주장이 아니라 증거(evidence over claims)" — 테스트 통과/실행 결과로 증명한다.

## Red Flags (이 생각이 들면 멈춰라 — 합리화 중이다)

| 생각 | 현실 |
|------|------|
| "테스트는 아마 통과할 거야" | 완료 직전 실제 검증 명령을 실행하라. |
| "맥락부터 좀 더 모아야겠어" | 프로세스 점검이 명료화 질문보다 먼저다. |
| "일단 코드베이스부터 둘러보자" | 어떻게 둘러볼지를 프로세스가 알려준다. 먼저 점검하라. |
| "이건 정식 절차까진 필요 없어" | 적용되는 절차가 있으면 쓴다. |
| "이거 하나만 먼저 하고" | 무엇이든 하기 전에 점검하라. |
| "근본 원인은 모르지만 이 수정이면 될 것 같아" | [[systematic-debugging]]으로 원인을 먼저 입증하라. |

## 스킬 유형

- **엄격(Rigid)** (TDD, 체계적 디버깅): 정확히 따른다. 규율을 적당히 풀지 마라.
- **유연(Flexible)** (패턴류): 원칙을 맥락에 맞게 적용한다.

## 핵심 원칙

- **한 번에 하나의 질문** — 질문 폭격 금지.
- **YAGNI 철저히** — 모든 설계에서 불필요한 기능 제거.
- **대안 탐색** — 정착 전 항상 2~3개 접근법 제시.
- **점진적 검증** — 설계 제시 후 승인을 받고 다음으로.
- **유연하게** — 말이 안 되면 돌아가서 다시 명료화.

> 사용자 지시는 *무엇(WHAT)*을 말하지 *어떻게(HOW)*를 말하지 않는다. "X 추가해"나 "Y 고쳐"가 워크플로를 건너뛰라는 뜻은 아니다.
