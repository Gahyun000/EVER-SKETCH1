# EVER-SKETCH 전환 계획 — 회차·배부 걷어내고 폴더·결재로

- 작성: 2026-09-03 · 상태: **검토용 초안 (코드 미착수)**
- 대상 저장소: `EVER-SKETCH1` ← 이식 원본: `ebook_html1`
- 이 문서는 합의를 위한 것이다. §11의 미결 쟁점이 닫히기 전에는 코드를 건드리지 않는다.

## 0. 한 줄 요약

**관리자가 밀어주는 축(회차·배부)을 걷어내고, 개인이 만들어 올리는 축(폴더·결재)으로 갈아탄다.**
표준 양식은 배부의 부속품에서 **독립된 생성 옵션**으로 승격한다.

```
[지금]  관리자가 회차를 열고 → 전원에게 1장씩 배부 → 작성 → 취합
[이후]  개인이 표준양식/빈슬라이드를 골라 만들고 → L1에게 제출 → 승인/반려 → 팀 공유
```

## 1. 현재 상태 진단

### 1.1 두 저장소의 성격 차이

| | `ebook_html1` (이식 원본) | `EVER-SKETCH1` (대상) |
|---|---|---|
| 인증 | **없음** — `src/shell/user.ts`의 이름 입력칸 하나 | 완성 (`server/auth.py`, 쿠키 `es_session`, HttpOnly) |
| 권한 | 없음 (누구나 승인 가능) | `permissions.decide()` 단일 판정, admin/writer/viewer |
| 자료 분류 | **Folders 트리** (`folder_id`) | **Cycles 회차** (`cycle_id` + `owner_id`) |
| 승인 | **Approvals 테이블 + round + 스냅샷** | `Projects.submit_status` 컬럼 (테이블 없음) |
| 코멘트 | `ApprovalComments` — 슬라이드 단위, 스냅샷에 붙음 | `Comments` — 요소/표 셀 앵커, 스레드·해결·고침 |
| 셸 | `src/shell/AppShell.tsx` 사이드바 3메뉴 | 없음 (`App.tsx`가 view 문자열로 분기) |
| 라우트 | `app.py` 단일 파일 인라인 | `routes_*.py` + `include_router` |

### 1.2 조사에서 나온 결정적 사실 5가지

1. **표준 양식은 이미 독립돼 있다.**
   `server/template_seed.py`는 서버 내 어떤 모듈도 import하지 않는 순수 함수 모듈이다.
   프런트 `src/template/slots.ts`도 `src/cycles/*`와 import 관계가 **한 줄도 없다.**
   회차와의 결합은 오직 **호출자** 쪽이다 — `cycles.py:236 distribute()`, `routes_cycles.py:390 preview`.

2. **`Templates` 테이블은 죽은 코드다.**
   `cycles.ensure_default_template()`이 회차 개설 때 한 번 굽지만, 배부는 이 레코드를 읽지 않고
   `template_seed.build_template_state()`를 다시 호출한다. `slot_policy` 컬럼을 읽는 코드도 없다.
   → 테이블·`TEMPLATE_MANAGE` 권한과 함께 통째로 버려도 표준 양식은 멀쩡하다.

3. **표준 양식이 세상에 나오는 유일한 통로가 회차 API 2개다.**
   `POST /api/cycles/{cid}/distribute`, `GET /api/cycles/{cid}/preview` — 둘 다 `cid`를 요구한다.
   **회차를 지우면서 새 진입점을 만들지 않으면 표준 양식은 사실상 죽는다.** 이번 작업의 유일한 필수 신규 코드다.

4. **`pptx_import.py:28`이 `template_seed`를 역참조한다** (`PAGE_W`, `PAGE_H`).
   → `template_seed.py`는 어떤 경우에도 삭제 금지.

5. **승인 개념이 이미 둘 있다.**
   `Projects.submit_status(draft/submitted/returned/approved)` vs `Approvals.status(pending/approved/rejected/withdrawn)`.
   의미가 겹친다. 그대로 얹으면 한 자료에 승인 상태가 두 개 생긴다. §4에서 하나로 정리한다.

### 1.3 실사용 데이터 규모 (마이그레이션 비용)

`server/ebook_html.db` — Users 5 (admin 1 / writer 4), Projects 11 (회차 소속 4), Comments 10,
Cycles 1, CycleDecks 1, Templates 1, ProjectVersions 0, 소유자 없는 프로젝트 0.
→ **데이터가 작다. 마이그레이션은 부담이 아니다.** 백업 후 진행하면 된다.

## 3. 목표 개념 모델

### 3.1 이번 설계의 핵심 아이디어 — 승인본과 작업본의 분리

> **L3은 `Projects`를 보지 않는다. `Approvals.snapshot`을 본다.**

`ebook_html1`의 결재는 요청 시점에 `Projects.state`를 통째로 얼려 `Approvals.snapshot`에 복사한다
(`server/approvals.py request()`). 이미지가 아니라 편집 가능한 페이지 JSON 그대로다.

이 구조가 D7의 요구("수정 중에 L3이 보던 자료가 사라지면 안 된다")를 **추가 장치 없이** 해결한다.

```
Projects.state   ← L2가 지금 고치고 있는 살아 있는 문서 (요동친다)
Approvals[승인].snapshot ← 얼어붙은 승인본 (L3이 보는 것, 절대 안 흔들림)
```

L2가 수정 중이어도 L3의 화면은 직전 승인본 그대로다. 재승인이 나야 비로소 교체된다.
「수정 중」 배지만 얹으면 L3도 "곧 바뀔 자료"임을 안다.

### 3.2 자료의 생애주기

```
                    ┌──────────────────────────────────────────┐
                    ↓                                          │
  [draft] ──제출──> [pending] ──반려──> [rejected] ──재제출─────┘
   편집O            편집X   │           편집O
   L3 X             L3 X   │           L3 X(첫 승인 전)
                           │
                         승인
                           ↓
                      [approved] ──────────────────────┐
                       편집X                            │
                       L3 O ← 승인 스냅샷              수정요청
                           ↑                            ↓
                           │                   [revision_pending]
                           │                    편집X · L3 O(이전 승인본)
                           │                            │
                        재승인                        L1 허락
                           │                            ↓
                    [pending(새 round)] <──재제출── [revising]
                     편집X · L3 O(이전 승인본)      편집O · L3 O(이전 승인본) + 「수정 중」 배지
```

**상태는 저장하지 않고 `Approvals` 최신 행에서 파생한다.** 진실이 한 곳에만 있게.

| 최신 결재 행 | 파생 상태 | L2 편집 | L3에게 | 배지 |
|---|---|---|---|---|
| 없음 / withdrawn | `draft` | O | 안 보임 | — |
| `kind=approval, pending` | `pending` | X | 직전 승인본(있으면) | 결재 중 |
| `kind=approval, rejected` | `rejected` | O | 직전 승인본(있으면) | 반려 |
| `kind=approval, approved` | `approved` | X | **승인본** | — |
| `kind=revision, pending` | `revision_pending` | X | 승인본 | 수정 요청 중 |
| `kind=revision, approved` | `revising` | O | 승인본 | **수정 중** |

### 3.3 폴더 두 종류

| | 개인 사설 폴더 | 팀 공유 폴더 |
|---|---|---|
| 소유 | 사용자 1명 (`owner_id`) | 팀 (`team_id`) |
| 만드는 사람 | 본인 | L1 |
| 보이는 사람 | 본인 + L1 | 팀원 전원 |
| 담기는 것 | 작업본 (`Projects`) | **승인본** (승인된 프로젝트가 `publish_folder_id`로 자리를 잡음) |
| 쓰기 | 본인 | 승인 시 시스템이 반영. 사람이 직접 넣지 않음 |

L2·L3 모두 개인 폴더를 갖는다. L3의 개인 폴더에는 빈 슬라이드 스케치만 들어간다(D3).

## 4. 데이터 모델

### 4.1 신설

```sql
-- 팀
CREATE TABLE Teams(
  id TEXT PRIMARY KEY,            -- 't'+uuid12
  name TEXT NOT NULL,
  lead_id TEXT,                   -- 담당 L1 (결재 라우팅의 기본값)
  created_by TEXT, created_at REAL NOT NULL, updated_at REAL);

CREATE TABLE TeamMembers(
  team_id TEXT NOT NULL, user_id TEXT NOT NULL,
  added_by TEXT, added_at REAL NOT NULL,
  PRIMARY KEY(team_id, user_id));
CREATE INDEX idx_tm_user ON TeamMembers(user_id);

-- 폴더 (ebook_html1 원본 + owner_id/team_id/kind 추가)
CREATE TABLE Folders(
  id TEXT PRIMARY KEY, name TEXT, parent_id TEXT,
  kind TEXT NOT NULL DEFAULT 'private',   -- 'private' | 'team'
  owner_id TEXT,                          -- kind='private'
  team_id TEXT,                           -- kind='team'
  created_at REAL, updated_at REAL);
CREATE INDEX idx_folders_parent ON Folders(parent_id);
CREATE INDEX idx_folders_owner  ON Folders(owner_id);
CREATE INDEX idx_folders_team   ON Folders(team_id);

-- 결재 (ebook_html1 원본 + kind/team_id, requester/approver를 user id로)
CREATE TABLE Approvals(
  id TEXT PRIMARY KEY, project_id TEXT, project_name TEXT, folder_path TEXT,
  kind TEXT NOT NULL DEFAULT 'approval',  -- 'approval' | 'revision'   ★신규
  team_id TEXT,                           -- 요청 시점 팀 고정            ★신규
  round INTEGER, status TEXT,             -- pending|approved|rejected|withdrawn
  requester TEXT, approver TEXT,          -- ★ 표시 이름 → Users.id 로 의미 변경
  request_message TEXT, decision_message TEXT,
  page_count INTEGER, snapshot TEXT,      -- kind='revision' 이면 snapshot NULL
  created_at REAL, updated_at REAL, decided_at REAL);

CREATE TABLE ApprovalComments(
  id TEXT PRIMARY KEY, approval_id TEXT,
  page_id INTEGER,                        -- NULL = 전체 의견
  page_no INTEGER, author TEXT, body TEXT, created_at REAL);
```

> `Approvals.snapshot`은 조회 컬럼 상수 `_COLS`에 **일부러 빠져 있다**(`get_approval`만 따로 붙여 읽음).
> `_COLS` 순서를 건드리면 `_row()`의 인덱스 접근이 전부 어긋난다. 이식할 때 손대지 말 것.

## 5. 권한 모델 재정의

### 5.1 `permissions.py` 구조 변경

```python
Actor(id, role, status, team_ids: tuple[str, ...])          # team_ids 추가
Resource(owner_id, team_id, approved, locked,               # 신규 4필드
         comment_author_id)

```

액션 상수:
- **제거** `CYCLE_MANAGE`, `TEMPLATE_MANAGE`

### 5.2 판정표

| 액션 | L1 admin | L2 writer | L3 viewer |
|---|---|---|---|
| READ | 전부 | **본인 자료만** | 본인 사설 스케치 + **같은 팀 승인본** |
| WRITE | 전부 | 본인 AND `not locked` | 본인 사설 스케치만 |
| DELETE | 전부 | 본인 AND 결재 이력 없음 | 본인 사설 스케치 (결재 이력 없음) |
| `TEMPLATE_USE` | O | O | **X** (D3) |
| `SUBMIT` | — | 본인 자료 | X |
| `DECIDE` | 같은 팀 | X | X |
| `REVISION_REQUEST` | — | 본인 승인본 | X |
| `REVISION_DECIDE` | 같은 팀 | X | X |
| `COMMENT_READ` / `WRITE` | 전부 | 본인 자료 | **X** (기존 계약 유지) |
| `TEAM_MANAGE` / `USER_MANAGE` / `SETTINGS_MANAGE` | O | X | X |
| `AI_USE` | O | O | 검토 필요 (§11-Q4) |

`locked` = 파생 상태가 `pending` / `approved` / `revision_pending` 중 하나.

### 6.3 변경

- `GET /api/projects` — `?folder=&all=` 추가. 응답에 `{projects, folders, path}` 3종.
  기존 `visibility` 필터와 `folder_id` 조건을 **AND로 결합**.

  `cycle_status` 제거.

### 6.4 오류 규약 통일 — 이식 시 필수 수정

`ebook_html1` 결재 API는 실패도 `200 + {"ok": false, "error": "..."}` 로 돌려준다.
`EVER-SKETCH1`은 `raise HTTPException(4xx)` 스타일이다.
프런트 `approvalApi.ts`의 `j()`는 `res.ok`만 검사하므로, 그대로 두면 403이 날 때
`throw new Error('API 403 ...')`가 사용자에게 원시 문구로 노출된다.

→ **EVER-SKETCH 스타일(4xx)로 통일하고 `approvalApi.ts`도 같이 고친다.**

## 9. 실행 순서

각 단계는 **끝에서 전체 테스트가 초록**이어야 다음으로 넘어간다.

| 단계 | 내용 | 완료 판정 |
|---|---|---|
| **P0** | DB 백업 · 작업 브랜치 · 현재 테스트 전량 통과 스냅샷 확보 | `pytest server` + `npm run test:unit` + `npm run e2e:all` 기준선 기록 |
| **P1** | **표준 양식 독립** — `POST /api/projects/from-template` 신설 + 「새로 만들기」 선택 모달 | 회차를 거치지 않고 표준 양식 이북이 만들어진다 |
| **P2** | **회차·배부 제거** — §8 삭제 목록 집행, `permissions.py` 회차 규칙 제거, DB DROP + 컬럼 정리 | `test_template_*` 3종 여전히 통과. 앱이 회차 없이 뜬다 |
| **P3** | **팀** — `Teams`/`TeamMembers` + 팀 관리 화면 + `Actor.team_ids` | L1이 팀을 편성하고 L2·L3을 넣을 수 있다 |
| **P4** | **개인 사설 폴더** — `Folders(kind='private')` + 폴더 탐색기 UI 이식 | 각자 자기 폴더 트리만 보인다. 남의 폴더명이 안 샌다 |
| **P5** | **결재 이식** — `approvals.py` + `routes_approvals.py` + `src/approvals/` + 셸 | L2 제출 → L1 승인/반려 + 슬라이드별 코멘트가 돈다 |
| **P6** | **팀 공유 + 가시성 전환** — `Folders(kind='team')`, `publish_folder_id`, `visible_project_filter` 교체 | L3이 같은 팀 승인본만 본다. 남의 팀·미승인 자료는 목록에도 없다 |
| **P7** | **수정 요청 흐름** — `Approvals.kind='revision'` + 상태 파생 + 「수정 중」 배지 | L2 수정 중에도 L3 화면이 직전 승인본으로 안 흔들린다 |
| **P8** | 테스트·문서 정리 — 계약 테스트 재작성, e2e 재구성, `README.md`/`AGENTS.md`/`start_docs` 갱신 | 전량 초록 + 문서가 실제 코드와 일치 |

**순서 근거**
- P1이 P2보다 **먼저**인 이유: 표준 양식 진입점을 먼저 만들어 놔야, 회차를 지우는 순간 표준 양식이 죽는 구간이 생기지 않는다.
- P3(팀)이 P6(가시성)보다 먼저인 이유: "같은 팀 승인본"의 팀이 없으면 가시성 규칙을 쓸 수가 없다.
- P5(결재)가 P6보다 먼저인 이유: 승인 개념이 있어야 "승인본"이 존재한다.

## 10. 위험

| # | 위험 | 대응 |
|---|---|---|
| R1 | **`delete_folder()`가 하위 프로젝트를 재귀 삭제한다.** 원본은 권한 개념이 0이라 남의 자료·승인본까지 지운다 | 소유자 검사 + "결재 이력 있는 자료가 있으면 거부" 가드 필수 |
| R2 | **결재 코멘트 앵커가 끊길 수 있다.** `ApprovalComments.page_id`는 스냅샷 페이지 id인데, `applyProject()`가 `reseedUids(st.pages)`로 id를 다시 뿌린다 | P5 착수 전에 `reseedUids` 동작 확인. 끊기면 스냅샷 id를 안정 키로 별도 보존 |
| R3 | **`admin은 전부 True` 계약.** `test_permissions.py::test_관리자는_전부_허용`이 못박고 있다. L1에게 팀 범위를 걸면 이 테스트부터 깨진다 | §11-Q2에서 먼저 결정 |
| R4 | **기존 계약 테스트 대량 파기.** `test_visibility.py`의 동료 열람 5개, `test_permissions.py` 열람자 3개 등 | 지우지 말고 **새 계약으로 다시 쓴다.** 테스트를 지우면 규칙이 사라진다 |
| R5 | **`test_endpoint_coverage.py`가 신규 라우트를 잡는다** — 모든 엔드포인트에 `require_active` + 권한 판정 호출 강제 | 이건 위험이 아니라 안전망. 이식 코드에 가드를 빼먹으면 즉시 잡힌다. 그대로 둔다 |
| R6 | **e2e 재작성 물량.** `approval_flow.mjs`는 로그인 없는 상태 전제(`.sh-side .sh-nav` 3개 단언 포함) | `login_password_smoke.mjs`의 로그인 헬퍼를 앞에 붙이고 역할별 시나리오로 재구성 |

| R8 | 프런트 두 축 충돌 — `useNav.menu` × `useProjects.view`. `LibView`의 `'cycles'` 값 제거 필요 | P2에서 `LibView`를 `'library' | 'editor'`로 축소한 뒤 P5에서 셸을 얹는다 |

## 11. 지금 결정이 필요한 것

| Q | 쟁점 | 기본안 |
|---|---|---|
| **Q1** | **L2는 동료의 승인본도 못 보는가?** "L2는 본인 자료만"을 문자 그대로 적용하면 팀 공유 폴더는 L3 전용이 된다. 승인된 자료는 팀원 전체 공개가 자연스러워 보이는데, 명시된 규칙과 어긋난다 | 엄격 적용(본인 것만). 팀 공유 폴더는 L1·L3만 열람 |
| **Q2** | **L1도 팀 범위에 갇히는가?** L1이 여러 명일 때, 남의 팀 자료까지 다 보고 결재할 수 있는가 | 결재는 같은 팀만, 열람은 전 팀 허용 |
| **Q3** | **L3의 개인 스케치를 본인이 삭제할 수 있는가?** 현재 L2조차 DELETE가 전면 금지다 | 결재 이력 없는 개인 자료는 본인 삭제 허용 |
| **Q4** | **L3에게 AI 기능을 주는가?** 현재 viewer는 `AI_USE` 거부다. 스케치를 하게 되면 필요할 수 있다 | 허용 |
| **Q5** | **표준 양식의 제출 기한 문구.** 회차가 사라지면 머리글의 `%m/%d` 기한 라벨을 채울 근거가 없다 | 비워 둔다. 필요하면 생성 시 직접 입력 |
| **Q6** | **팀 공유 폴더 게시 위치를 누가 고르는가?** 제출할 때 L2가? 승인할 때 L1이? | L2가 제출 시 선택, L1이 승인 시 변경 가능 |
| **Q7** | **기존 회차 자료 4건**(`cycle_id` 있는 Projects)을 어떻게 넘길 것인가 | 소유자의 개인 폴더로 이관, `cycle_id`만 버림 |
