26.08.18

ebook_sketch — 월간 임원회의 자료 협업 플랫폼 기획의도 · 설계사상 · 로드맵

통합 대상: ebook_html(React·TS 편집기 + FastAPI) · uniever_ebook(이북/덱 생성기) · default_skill(표준스킬 43종)  |  작성: 유니에버 AI팀

한 문장 요약 — 월 1회 임원회의 자료를 "파일로 주고받는 일"에서 "링크 하나 위에서 같이 고치는 일"로 바꾼다. 임원 각자에게 고정 표준 템플릿 1장이 부여되고, 그 자리에서 고치고, 관리자가 열람하며 메모로 피드백하고, 작성자가 즉시 반영한다. PPT 왕복은 사라진다.

1. 기획의도 Why & Background

문제 인식 — 지금 무엇이 불편한가

월 1회 임원회의 자료는 내용이 어려워서 힘든 게 아니다. 내용을 만드는 시간보다 파일을 돌리는 시간이 더 길다.

PPT 작성→ 메일·메신저 발송→ 검사·코멘트(구두/메일)→ 수정→ 재발송→ 버전 혼선→ 취합·양식 정리
  • 왕복 비용 — 작성 → 발송 → 검사 → 수정 → 재발송이 회차마다 반복된다. 실제 소요의 대부분이 이 왕복이다.
  • 버전 분열 — 최종.pptx, 최종_수정.pptx, 최종_진짜최종.pptx. 어느 것이 원본인지 사람이 기억으로 관리한다.
  • 피드백 유실 — 코멘트가 문서 밖(메일·구두·메신저)에 있어 어느 장, 어느 칸 이야기인지 다시 물어야 한다. 반영 여부도 추적되지 않는다.
  • 양식 이탈 — 임원별로 표 모양·글꼴·색이 달라져 취합 단계에서 관리자가 손으로 다시 맞춘다.
  • 열람 통제 부재 — 파일이 나가는 순간 누가 보고 누가 고칠 수 있는지 통제할 방법이 없다.

해결 목표 — 이 프로젝트로 무엇을 바꾸는가

AS-IS

  • 파일이 이동한다 (첨부·다운로드)
  • 피드백은 문서 밖에 있다
  • 원본은 사람의 기억 속에 있다
  • 양식은 권고사항이다
  • 취합은 관리자의 수작업이다

TO-BE

  • 사람이 링크로 모인다 (원본 1개)
  • 피드백은 그 페이지·그 칸에 붙는다
  • 원본은 서버가 보증한다 (버전 자동기록)
  • 양식은 시스템이 고정한다
  • 취합은 발행 버튼 한 번이다

정량 목표(파일럿 1회차 기준 가설): 자료 준비 리드타임 50% 단축, 재발송 횟수 0회, 취합·양식정리 수작업 시간 80% 감소. 파일럿에서 실측해 조정한다.

존재 이유 — 왜 지금, 왜 우리가 만드는가

  • 재료가 이미 있다. 편집기(ebook_html), 이북·덱 생성기(uniever_ebook), 개발표준(default_skill) 3종이 각각 동작한다. 새로 만드는 게 아니라 이어 붙여 제품으로 만드는 단계다.
  • 범용 협업툴로는 안 된다. 상용 도구는 회의체 고유의 고정 표준 양식 + 임원 1인 1장 + 회차 취합 + 이북/PPT 산출이라는 흐름을 그대로 담지 못한다.
  • 사내 파일럿이 곧 레퍼런스다. 유니에버 임원회의에서 검증한 흐름은 그대로 사내 표준 → 상품(솔루션 사업)으로 확장할 수 있다. 이번 프로젝트의 최종 목적지는 사내 도구가 아니라 비즈니스 모델이다.

2. 설계사상 Philosophy & Principle

핵심 철학 — 다섯 개의 문장

원칙의미와 결과
① 원본은 하나다
Single Source of Truth		 문서는 이동하지 않는다. 사람이 링크로 온다. 파일 첨부는 최종 산출(발행) 단계에서만 발생한다. 버전은 서버가 자동 기록한다.
② 권한은 화면이 아니라 데이터에 붙는다 버튼을 숨기는 것은 UX이고, 막는 것은 API다. 모든 읽기·쓰기·삭제는 서버에서 소유자·레벨을 검증한다. 프런트 가드는 보조 수단일 뿐이다.
③ 피드백은 문서 안에서 닫힌다 메모는 반드시 페이지(또는 셀)에 앵커된다. 남기기 → 보기 → 고치기 → 해결까지 한 화면에서 끝난다. 문서 밖으로 나가는 코멘트는 만들지 않는다.
④ 자유도는 의도적으로 제한한다 표준 양식은 시스템이 박아둔다. 사용자는 칸 안의 내용, 셀 병합·추가, 글자 크기·굵기 수준까지만 만진다. 자유도를 줄여야 취합이 자동화된다.
⑤ 되돌릴 수 있어야 손이 빨라진다 자동 저장 + 버전 스냅샷 + 복원이 기본. 실수를 되돌릴 수 있다는 확신이 있어야 사용자가 과감히 고친다.

우선순위 — 가치가 충돌할 때

정확성(원본 무결) > 권한·보안 > 취합 자동화 > 편집 자유도 > 화면의 화려함

  • "임원이 원하는 대로 다 편집되게" 와 "취합이 자동으로" 가 충돌하면 → 취합 자동화가 이긴다. 편집 자유는 예외 요청으로 관리자 승인 후 확장한다.
  • "빨리 쓰게 로그인 없이" 와 "누가 무엇을 봤는가" 가 충돌하면 → 권한이 이긴다. 임원 발표자료는 열람 이력이 남아야 한다.
  • "신규 기능 추가" 와 "기존 산출 경로 유지" 가 충돌하면 → 기존 산출 경로가 이긴다. 아래 무수정 계약을 참조.

기술 · 구조 원칙

  • 스택 고정 — React + TypeScript + Vite(프런트) / FastAPI + SQLite(백엔드). 현재 ebook_html 구조를 그대로 계승하고, 사내 서버 + 자체 계정(ID/PW) 인증을 얹는다.
  • 무수정 계약 유지 — uniever_ebook의 생성기(generator.py, 덱 빌더)는 수정하지 않는다. 연결은 기존 계약(PNG 폴더 산출 → CLI 호출)을 그대로 쓴다. 통합의 방향은 "합치기"가 아니라 "호출하기"다.
  • 단일 상태 모델 — 페이지 = 카드 + 자유 캔버스 요소. 이북 1장 = PNG 1장이라는 기존 렌더 계약을 유지해 편집·발표·이북·PPTX 산출이 하나의 상태에서 나온다.
  • 표준스킬 준수 — default_skill의 개발표준(UI 표준, G0~G6 게이트, 검증 증적)을 개발 프로세스에 그대로 적용한다. 화면 작업은 uniever-development-standard 필수 경유.
  • 확장 여지만 열어둔다 — SSO/AD 연동, PostgreSQL 전환, 멀티테넌시(외부 고객사)는 인터페이스만 분리해 두고 구현은 뒤로 미룬다. 지금 만들지 않는다.

4. 핵심 기능 ① — 권한 3레벨

기존 ebook_html과의 가장 큰 차이. 지금 시스템에는 사용자 개념 자체가 없다(프로젝트에 소유자가 없음). 여기에 계정·소유·레벨을 도입한다.

레벨대상권한보이는 범위
L3 관리자회의 주관·기획 담당 작성 · 수정 · 삭제 + 사용자 관리(계정 생성·레벨 변경·비활성화) + 회차 개설/마감 + 템플릿 배부 + 전체 이북 열람 + 메모 작성·해결 + 최종 발행 전체
L2 작성자임원 · 부서 담당자 작성 · 수정 (본인 이북) + 본인 이북에 달린 메모 확인·답글·해결 요청. 삭제 불가, 타인 이북 접근 불가 본인 이북 + 공개된 회차 결과물
L1 열람자일반 참석자·공유 대상 읽기 전용. 편집·삭제·메모 작성 불가(메모 열람도 기본 차단, 관리자 설정으로 열람만 허용 가능) 발행된 회차 결과물

권한 설계 규칙

  • 소유 기반 — 모든 이북에 owner_id가 붙는다. L2는 "내 것"만, L3는 "전부". 판정은 서버 미들웨어 한 곳에서 한다.
  • 삭제는 L3만 — L2의 삭제 요청은 "삭제 요청" 상태로 남기고 실제 삭제는 L3가 승인한다(회차 자료 유실 방지).
  • 이력 필수 — 로그인, 열람, 편집, 발행, 권한 변경은 감사 로그에 남는다. 임원 자료 특성상 "누가 봤는가"가 요구된다.
  • 초기 계정 — 관리자 1명을 시드로 생성하고, 이후 모든 계정은 관리자 화면에서 발급한다. 자가 가입은 만들지 않는다.

5. 핵심 기능 ② — 노션식 메모 피드백 루프

현재 ebook_html의 메모는 프로젝트 단위 메모장이다. 이를 페이지·셀에 붙는 코멘트로 확장하고 상태를 부여한다.

L3 관리자: 페이지에 메모→ L2 작성자 알림(배지)→ 그 자리에서 즉시 수정→ "수정함" 표시→ L3 확인 → 해결(closed)
항목정의
앵커이북 > 페이지 > (선택)요소·셀 좌표. 클릭하면 해당 위치로 스크롤·하이라이트
상태열림 → 수정함 → 해결 (해결 권한은 메모 작성자 또는 L3)
작성 권한L3 전원 / L2는 본인 이북에 한해 답글. L1은 작성 불가
알림1단계는 화면 내 배지 + 미해결 목록(폴링). 메일·메신저 연동은 2단계 검토
이력메모·답글·해결은 삭제해도 이력에 남는다. 회차 종료 시 "미해결 N건" 요약

6. 핵심 기능 ③ — 고정 표준 템플릿과 편집 범위

회차가 열리면 임원 1인당 표준 템플릿 1장이 자동으로 부여된다(예: 로드맵/마일스톤 표 + 진행현황 + 향후계획 + 이슈리스트 양식). 사용자는 그 위에서만 작업한다.

구분허용차단
표셀 내용 입력, 셀 병합·해제, 행·열 추가·삭제, 셀 정렬, 셀 배경색표 삭제, 표준 헤더 행 변경(관리자만)
글자크기, 굵게, 기울임, 밑줄, 색, 정렬 — 한글(HWP)식 즉시 서식임의 폰트 교체(브랜드 폰트 세트 내에서만 선택)
레이아웃지정 영역 내 요소 이동·크기 조절페이지 규격·표지·목차 구조 변경(관리자만)
페이지—페이지 추가·삭제(1인 1장 원칙, 예외는 관리자 승인)

이미 구현되어 있는 것: 셀 병합/해제, 행·열 추가·삭제, 셀 정렬은 src/canvas/tableOps.ts에 순수 함수로 존재한다. 서식 툴바(EditToolbar, ClassicBar)도 있다. 이번 단계 작업은 새 구현이 아니라 "표준 템플릿 위에서의 권한별 제한 모드" 추가다.

1.5주		편집 제한 모드 표준 템플릿 잠금 영역 정의, 권한별 편집 허용 범위 적용(표·서식은 허용, 구조는 차단), 서식 툴바 정리 및 UI 표준 점검 L2 계정으로 금지 동작 차단 확인
P5
1.5주		취합 · 발행 회차 마감 → 임원별 1장 자동 병합 → 이북(PNG→generator.py) · PPTX · PDF 산출, 발행본 L1 공개, 감사 로그 발행 1건 무오류 산출
P6
1주		파일럿 · 인수 실제 월간 회의 1회 리허설 운영, 사용자 교육 1시간, 이슈 수집·수정, 운영 매뉴얼·인수인계 문서 실회의 1회 완주 + 정량 목표 측정

총 약 11주(순차 기준). P3와 P4는 부분 병행 가능하여 실제 9~10주 압축 여지가 있다. 각 단계 종료 시 default_skill 표준의 검증 증적을 남긴다.

이후 확장 (파일럿 이후 검토)

  • 사내 SSO/AD 연동, PostgreSQL 전환, 동시 편집(실시간 커서)
  • AI 보조: 지난 회차 대비 변경점 요약, 이슈리스트 자동 초안, 문체 정리
  • 상품화 — 멀티테넌시 + 조직·템플릿 커스터마이징 → 사외 판매 가능한 "회의체 문서 협업" 솔루션

9. 리스크와 대응

리스크대응
임원이 웹 편집기를 쓰지 않고 PPT를 고집템플릿을 "이미 채워진 상태"로 배부해 진입장벽 제거. 최종 PPTX 내보내기를 항상 보장. 교육 1회 + 관리자 대리입력 경로 유지
편집 기능이 PPT만 못하다는 불만범위를 명시적으로 좁힌다(표·서식 수준). 초과 요구는 관리자 승인 후 템플릿 자체를 개선하는 방식으로 흡수
기존 ebook_html 데이터(소유자 없는 프로젝트) 이관P1에서 일괄 관리자 소유로 이관 후 재배정. 이관 스크립트와 롤백 스냅샷 필수
권한 우회(프런트만 막고 API 노출)서버 가드를 단일 지점에 두고, 각 엔드포인트에 대해 L1/L2/L3 3계정 자동 테스트를 회귀 스위트로 고정
uniever_ebook 생성기 변경 유혹무수정 계약 유지. 필요한 변형은 호출 측(폴더·옵션)에서 해결
회의 일정 고정(월 1회)으로 실패 시 한 달 대기P6 이전에 가상 회차로 2회 리허설. 실회의는 기존 PPT 프로세스와 1회 병행 운영

10. 지금 결정이 필요한 것

  1. 표준 템플릿 정본 — 첨부하신 로드맵/마일스톤 + 진행현황 + 향후계획 + 이슈리스트 양식을 그대로 정본으로 확정할지, 항목을 조정할지.
  2. 대상 인원 — 1회차에 참여하는 임원(L2) 수와 열람자(L1) 범위. 회차당 페이지 수 산정의 기준이 된다.
  3. 저장소 전략 — ebook_html을 ebook_sketch로 개명·확장할지, 새 저장소를 만들고 두 자산을 이식할지.
  4. 서버 위치 — 사내 어느 서버에 올릴지, 포트·도메인·백업 정책(SQLite 파일 백업 주기).
  5. L1의 메모 열람 허용 여부 — 열람자에게 피드백 내역을 보일지 감출지(기본안: 감춤).
  6. 파일럿 회차 — 9월 회의를 병행 운영 대상으로 삼을지, 10월로 잡을지. P0 착수일이 여기서 역산된다.
