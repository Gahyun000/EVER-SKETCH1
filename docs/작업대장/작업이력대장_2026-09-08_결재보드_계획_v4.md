# 작업이력대장 - 결재 보드 계획 (v4 — 결재함에 둔다)

- [x] 년월일: 2026-09-08
- [x] v3 와 다른 점: 보드를 **「내 자료」가 아니라 「결재함」**에 둔다.
- [x] 상태: **계획만.**

---

## 1. 지적이 맞습니다 — 그리고 v3 의 문제 하나가 같이 사라집니다

「내 자료」에 보드를 넣으면 **같은 화면인데 사람마다 다릅니다.**
관리자·작성자는 보기 전환이 있고 열람자는 없습니다. 그건 어색합니다.

**결재함은 다릅니다.** 지금도 **열람자에게는 버튼 자체가 없습니다**
(`{canSubmit && <결재함 버튼>}` — 작성자·관리자만). 화면이 통째로 없는 것은
이미 자연스럽고, 아무도 「왜 나만 다르지」라고 묻지 않습니다.

### 그리고 v3 이 걱정하던 것이 없어집니다

v3 에서 「관리자에게는 칸 뜻이 뒤집힌다」고 적었습니다 —
작성자에게 「제출」인 것이 관리자에게는 「결정할 것」이라고요.

**결재함의 칸 이름은 역할 중립적입니다.**

| 칸 | 작성자에게 | 관리자에게 |
|---|---|---|
| **제출** | 내가 낸 것, 답을 기다림 | 내가 결정할 것 |
| **반려** | 고쳐야 함 | 돌려보냈음 |
| **승인** | 끝 | 끝 |
| **거둠** | 내가 거둠 | 거둬 갔음 |

**둘 다 맞는 말입니다.** 「제출」은 「낸 상태」라는 사실을 말할 뿐,
누구 차례인지를 말하지 않습니다. 그래서 한 이름으로 둘을 다 담습니다.
**보드가 하나면 됩니다.**

---

## 2. 그런데 — 결재함은 「자료」가 아니라 「결재 건」의 목록입니다

이게 이번 계획에서 가장 중요한 대목입니다.

`list_approvals()` 는 `Approvals` 표를 그대로 돌려줍니다. **한 자료가 여러 줄입니다.**
지금 데이터베이스를 세어 봤습니다:

```
2026년 10월 임원회의 — 김가현    1회차 반려
2026년 10월 임원회의 — 김가현    2회차 대기      ← 같은 자료, 두 줄
제목 없음                       1회차 반려
제목 없음                       2회차 대기      ← 같은 자료, 두 줄
```

### 그래서 탭을 그대로 칸으로 펴면 원하신 것이 안 됩니다

```
        제출              반려              승인
   ┌──────────┐    ┌──────────┐    ┌──────────┐
   │ 10월 2회차│    │ 10월 1회차│    │          │
   └──────────┘    └──────────┘    └──────────┘
        ↑ 같은 자료가 두 칸에 동시에 있다
```

승인이 나면 2회차가 승인 칸으로 가지만 **1회차는 반려 칸에 그대로 남습니다.**
「반려에서 승인으로 **간다**」가 아니라 **「반려에도 있고 승인에도 있다」**가 됩니다.

말씀하신 노션의 그 느낌이 정확히 여기서 깨집니다.

---

## 3. 해법 — 칸에는 **자료별 최신 건**만 놓습니다

```
        제출              반려              승인
   ┌──────────────┐  ┌──────────┐   ┌──────────┐
   │ 10월 임원회의 │  │          │   │          │
   │ 2회차         │  │          │   │          │
   │ 1회차 반려 ›  │  │          │   │          │
   └──────────────┘  └──────────┘   └──────────┘
     ↑ 지난 회차는 카드 안에 한 줄로. 칸에는 안 놓는다.
```

- **칸에 놓이는 것** — 자료마다 **가장 최근 결재 건 하나**
- **지난 회차** — 그 카드 안에 「1회차 반려 · 9/7」처럼 한 줄. 눌러서 펼침
- 승인이 나면 **그 카드가 통째로 승인 칸으로** 옮겨집니다 ✓

**이력을 잃지 않으면서 카드가 옮겨집니다.**

### 지난 회차를 전부 보고 싶을 때는

**결재함에도 보기 전환을 둡니다** — `[목록] [보드]`.

- **목록** — 지금 그대로. 모든 결재 건. 탭(대기/승인/반려/거둠)도 그대로.
- **보드** — 자료별 최신 건.

「목록은 기존대로 두고」라고 하신 원칙을 **결재함 안에서도** 그대로 씁니다.

---

## 4. 그러면 「내 자료」는

**손대지 않습니다.** 지금 목록 그대로입니다.

자료 목록에는 이미 상태 칩(「결재 중 2회차」·「반려」·「잠김」)이 있습니다.
보드는 결재함에 있고, 목록은 「내 자료가 어디에 얼마나 있나」를 봅니다.
**두 화면이 서로 다른 일을 합니다.**

---

## 5. 만들 것

| 조각 | 새로 만드나 |
|---|---|
| 서버 | **아무것도 안 고침** |
| 결재 건 목록 | `apiListApprovals()` 그대로 — 이미 `counts` 도 준다 |
| **자료별 최신 건 고르기** | **새로** — 순수 함수 |
| **status → 칸** | **새로** — 순수 함수(작다) |
| 보드 화면 | 새로 — 칸 넷 · 카드 · 건수 |
| 보기 전환 | 새로 (결재함 안) |
| 지난 회차 펼치기 | 새로 |
| 끌기 | **없음** |

### 순수 함수 둘

```
latestPerProject(approvals)  → 자료마다 가장 최근 건 하나 + 지난 회차 목록
columnOf(status)             → '제출' | '반려' | '승인' | '거둠'
```

`latestPerProject` 가 **이 계획의 핵심**입니다. 여기가 틀리면
같은 자료가 두 칸에 뜨거나, 최신이 아닌 회차가 칸에 앉습니다.
**같은 자료·같은 시각** 같은 경계도 정해 둬야 합니다 —
`node` 로 바로 시험할 수 있게 화면과 떼어 놓습니다.

### 「수정 요청」 건을 어떻게 셀지도 여기서 정해야 합니다

`Approvals` 에는 두 종류가 있습니다(`kind`).

- `approval` — 문서를 낸 것
- `revision` — 「고치게 해 달라」고 청한 것. **문서가 아니라 허락 요청**이라
  `snapshot` 이 없고 회차도 안 셉니다

**보드의 「최신 건」에 수정 요청을 포함할지**를 정해야 합니다.
포함하면 승인된 자료가 「제출」 칸으로 잠깐 갔다가 돌아옵니다 — 그게 맞는 그림입니다
(허락을 기다리는 중이니까). **포함을 권합니다.**

---

## 6. 위험

| 위험 | 왜 | 대응 |
|---|---|---|
| **같은 자료가 두 칸에** | 최신 고르기가 틀리면 | `latestPerProject` 를 검사로 못박는다. **한 자료는 한 칸에만** |
| 관리자 결재함이 크다 | 전체 팀 건이 다 온다 | 자료별 최신만 놓으므로 오히려 줄어든다. 팀·기간 거르기는 목록 쪽 |
| 지난 회차가 안 보인다 | 칸에서 뺐으니 | 카드 안에 한 줄 + 목록 보기는 그대로 |
| **반려 사유가 없다** | — | **결재함은 다르다.** `apiGetApproval` 로 상세를 보고 있어서 사유가 **이미 있다** |

**반려 사유 문제가 여기서는 없습니다.** 이건 결재함에 두는 것의 뜻밖의 이점입니다 —
`/status-map` 에는 사유가 없었지만, 결재 건 목록에는 `decision_message` 가 붙어 있습니다.
착수계획 B-1 은 **편집 화면 카드** 때문에 여전히 남지만, 보드 때문에 서두를 이유는 없어집니다.

---

## 7. 순서

```
1. latestPerProject + columnOf + 검사      ← 여기가 제일 중요하다
2. 결재함 보드 + 보기 전환
3. 지난 회차 펼치기
4. 창 다시 볼 때 갱신
```

## 9. v1~v3 과의 관계

| | 무엇을 했나 | 왜 버렸나 |
|---|---|---|
| v1 | 끌어서 상태를 바꾼다 | 상태는 결재 이력에서 계산된다. 끌 수 없다 |
| v2 | 끌기를 뺐다 | 방향은 맞았다 |
| v3 | 「내 자료」에 보드, 역할별 기준 | 같은 화면인데 사람마다 달랐다 |
| **v4** | **결재함에 보드, 자료별 최신 건** | — |

**v4 가 v3 보다 단순합니다.** 보드가 둘에서 하나로 줄었고,
칸 이름이 역할 중립적이 되었고, 반려 사유 문제가 없어졌습니다.
「일관성이 없어 보인다」는 지적 하나가 세 가지를 같이 풀었습니다.
