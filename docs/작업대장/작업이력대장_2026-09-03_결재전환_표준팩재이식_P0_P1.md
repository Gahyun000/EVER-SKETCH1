## P6 — 팀 공유 + 가시성 전환 (서버) (2026-09-04)

- [x] 년월일: 2026-09-04
- [x] 요청내용: 「이어서 진행해」 — P6. 승인본이 실제로 같은 팀에 뜨게 한다.

### 이 단계가 하는 일 — 한 문장

**팀이 보는 것은 `Projects` 가 아니라 `Approvals.snapshot` 이다**(전환계획 §3.1).

```
Projects.state            ← 작성자가 지금 고치는 살아 있는 문서. 요동친다.
Approvals[승인].snapshot   ← 제출 순간에 얼어붙은 승인본. 팀이 보는 것.
```

작업본을 그대로 보여 줬다면 「어제 승인한 것과 다른 게 떠 있다」가 매일 일어난다.
승인은 **그때 그 문서**에 대한 승인이지 그 문서 이름표에 대한 승인이 아니다.

### 설계 판단 ① — D18·D19·D22·D23 이 규칙 **하나**로 줄었다

계획서에는 결정이 넷으로 적혀 있다(자료는 만들어진 팀의 것 / 현재·이전 표시 /
`팀·작성자명·월` 묶음 / 이전 팀에서는 본인 것만). 코드로 옮기면서 보니
**가시성 부분은 전부 한 문장의 따름결과**였다:

> 관리자 전부 / 내가 낸 건 / **지금 내 팀의 승인본**

`permissions.can_see_approval(actor, approval)` 한 함수로 적었다. 그 결과
**D23(이전 팀에서는 본인 것만)을 위한 코드가 `team_library.py` 에 한 줄도 없다** —
「같은 팀」을 *지금* 소속으로 판정하므로, 지금 내 팀이 아닌 팀의 자료가 목록에 남아
있을 수 있는 경로는 「내가 낸 것」밖에 없기 때문이다. 따로 걸렀다면 규칙이 두 벌이 되고,
두 벌은 언젠가 어긋난다.

- [x] 그 한 함수를 **결재 API 와 팀 공유가 함께 쓴다.** 두 곳이 각자 적으면
      「팀 공유에는 뜨는데 열면 404」 가 생긴다. `test_결재함과_팀공유가_같은_규칙을_쓴다` 가 지킨다.

### 설계 판단 ② — 결재함은 화면이고, 가시성은 권한이다

`can_see_approval` 을 그대로 결재함 목록에 꽂으면 같은 팀 남의 승인본이 결재함에 섞인다.
결재함이 답하는 질문은 「**내가 낸 것**이 지금 어떻게 됐나」 하나다 — 남의 승인본이
거기 섞이면 그 답이 목록 어딘가에 묻힌다. 그래서 목록은 `_my_box()` 로 좁히되,
**좁은 이유가 권한이 아니라 화면임을 코드에 적었다.** `_my_box` ∪ 팀 공유 =
`can_see_approval` 이 허용하는 전부 — 빠지는 건 없다.

### 설계 판단 ③ — 자료는 팀의 것이지만 **대화는 아니다**

같은 팀 사람이 승인본을 열 수 있게 되자 결재 코멘트도 함께 열렸다.
「3쪽 수치가 작년 것입니다」 같은 지적이 팀 전체에 흐르면
**사람들이 결재함에서 솔직하게 지적하기를 그만둔다.**
`can_see_approval` 보다 한 칸 좁은 `can_see_approval_thread`(당사자만)를 따로 두고,
남에게는 `comments: []` + `comments_hidden: true` + `comment_count` 를 준다 —
**감춘 사실 자체는 감추지 않는다.**

### 설계 판단 ④ — 관리자에게 남의 팀은 「이전 팀」이 아니다

`relation` 을 「현재 / 이전」 둘로만 두면 관리자 화면의 모든 팀이 「이전 팀」이 된다.
관리자는 그 팀에 있었던 적이 없을 수 있고, **팀 소속 이력을 저장하지 않으므로 알 방법도 없다.**
없는 근거로 「이전 팀입니다」라고 쓰는 것은 추측을 사실처럼 적는 것이라
`OTHER`(다른 팀)를 셋째 값으로 뒀다. 「이전」은 *내가 낸 자료가 거기 있을 때*만 쓴다 —
그것이 「내가 거기 있었다」의 유일한 증거다.

### 설계 판단 ⑤ — 월은 **승인 시각**으로 묶는다

9월 30일에 내고 10월 2일에 승인됐다면 그 자료가 팀에 **존재하게 된 것**은 10월이다.
그리고 한 자료는 **최신 승인본 1건만** 뜬다 — 3차까지 승인된 자료가 셋으로 늘어서면
「어느 게 최신인가」를 사람이 매번 판단해야 한다. 과거분은 지운 게 아니라 목록에서
뺀 것이고, `/history/{project_id}` 로 거슬러 올라간다(스냅샷은 안 싣는다 —
회차마다 문서 전체가 딸려 나온다).

## P7 — 수정 요청 흐름 (서버) (2026-09-04)

- [x] 년월일: 2026-09-04
- [x] 요청내용: 「이어서 진행해」 — P7. 승인된 자료를 고치는 길을 만든다.

### 이 단계가 지키는 것 — 한 문장

**승인된 자료를 고치는 동안에도 팀이 보던 그림은 안 흔들린다**(D8).
승인본은 얼어 있고, 열리는 것은 작업본뿐이다.

### 설계 판단 ① — 상태를 **저장하지 않는다**

`Projects` 에 상태 칼럼을 두면 진실이 두 곳이 된다: 결재 행과 그 칼럼.
둘은 반드시 어긋난다(승인이 반쯤 실패하거나, 결재를 고치는 경로가 하나 더 생기거나,
마이그레이션이 한쪽만 건드리는 순간에). **어긋나면 어느 쪽이 맞는지 알 방법이 없다.**

그래서 `server/doc_state.py` — **최신 결재 행 하나에서 계산하는 순수 함수**다.
DB 도 FastAPI 도 모른다(`permissions.py` 와 같은 이유: 테스트가 쉬우니 실제로 테스트된다).
이력 전체를 훑지 않고 **최신 행 하나만** 본다 — 훑으면 같은 이력으로도 훑는 순서에 따라
다른 답이 나올 수 있고, 최신 행 하나면 답이 하나다.

### 설계 판단 ② — 수정 요청 행에는 **스냅샷이 없다**

「이 문서를 고치겠다」는 **허락을 청하는 행**이지 문서 그 자체가 아니다.
그래서 `snapshot IS NULL` 이고, **그 덕에 D8 이 추가 장치 없이 풀린다** —
팀이 보는 그림은 수정 요청과 무관하게 직전 승인본 그대로고, 화면에는
「수정 중」 **글자만** 얹힌다. 그림을 바꾸는 것이 아니라 글자를 얹는 것이다.

### 설계 판단 ③ — 「수정 중」이 **영원히 남는 구멍**을 막았다

계획서에 없던 상태다. 허락받고 안 고치면 자료는 「수정 중」인 채로 멈추고,
팀은 몇 달째 「곧 바뀐다」는 글자를 단 승인본을 보게 된다 — **그 글자는 아무 뜻도 없다.**
`end_revision`(「수정 그만두기」)을 넣었다. **고친 내용은 안 지운다** —
남의 작업을 대신 버리지 않는다. 승인본은 애초에 손대지 않았으므로
팀 화면에는 아무 일도 일어나지 않는다.

- [x] **관리자라도 남의 수정을 대신 그만두지 못한다.** 그만두는 것은 「안 고치겠다」는
      뜻이고, 그 판단은 고치는 사람 몫이다(라우트가 404).

### 설계 판단 ④ — 거절·포기는 **있던 그대로**로 되돌린다

계획서 표에 없던 두 칸(`revision·rejected`, `revision·withdrawn`)이다.
`draft` 로 떨어뜨리면 **승인받은 자료의 잠금이 거절 한 번에 풀린다.**
수정 요청은 승인본이 있어야만 낼 수 있으므로 되돌아갈 자리가 승인본뿐이다.

### 게이트가 잡은 것 — 문서와 코드가 어긋났다

`request_revision` 의 주석에 「**회차는 올리지 않는다**」고 적어 놓고,
정작 `request()` 의 `round = COUNT(*) + 1` 은 수정 요청 행까지 세고 있었다.
그래서 승인본이 2건인데 「3회차」가 됐다 — 그때부터 「3회차 승인본」이 무엇을
가리키는지 알 수 없어진다. `kind='approval'` 만 세도록 고쳤다.
**적어 둔 것을 코드가 안 지키고 있었고, 테스트가 그걸 잡았다.**

### 팀 공유가 조용히 깨질 뻔한 자리

수정 **허락** 행도 `status='approved'` 가 된다. 걸러 내지 않으면
**스냅샷 없는 빈 자료가 팀 목록에 하나 더 뜬다** — 눌러도 아무것도 안 나오는 줄이다.
`team_library` 가 `kind='approval'` 만 읽도록 하고, 이력에서도 같이 걸렀다
(「몇 번째 승인본인가」를 세는 자리라서).

### 잠금의 경계 — 무엇을 왜 잠그는가

잠그는 이유는 **결재자·팀이 본 것과 작성자가 가진 것이 갈라지지 않게** 하는 것이다.

| 상태 | 잠금 | 이유 |
|---|---|---|
| `pending` | 🔒 | 결재자가 지금 보고 있다 |
| `approved` | 🔒 | 팀이 보고 있다 |
| `revision_pending` | 🔒 | 허락을 기다리는 중 — 여기서 열면 「요청」이 형식이 된다 |
| `rejected` | 열림 | **고치라고 돌려준 것**이다 |
| `revising` | 열림 | **고치라고 허락한 것**이다 |
| `draft` | 열림 | 아무도 안 봤다 |

## P7 — 수정 요청 흐름 (화면) (2026-09-04)

- [x] 년월일: 2026-09-04
- [x] 요청내용: 「이어서 진행해」 — P7 화면.

### 화면이 지키는 한 문장

**그림은 안 바뀌고 글자만 얹힌다.** 「수정 중」은 팀 화면의 자료를 바꾸는 것이
아니라 그 위에 붙는 글자다 — D8 이 화면에 나타나는 방식이 이것이다.

### 칩이 그리는 것을 `status` 에서 **파생 상태**로 바꿨다

`status` 는 결재 행 **하나**의 상태다. 수정 요청이 걸린 자료는 최신 승인 행이
`approved` 라서 칩에 「승인」이라고 적히는데, 실제로는 「수정 중」이다.
서버가 계산한 `state` 를 그대로 그린다 — **화면이 또 짜맞추면 두 벌이 되고,
그때 사용자에게는 「목록엔 승인됨인데 열면 수정 중」으로 보인다.**

- [x] 서버(`doc_state.LABEL`)와 화면(`DOC_STATE_LABEL`)이 **같은 글자**를 쓰는지
      테스트가 대조한다. 한쪽만 고치면 걸린다.

### 잠긴 자료에는 **자물쇠 + 「잠김」 글자**

배지가 없는 상태(승인됨)일수록 이 자물쇠가 **왜 안 고쳐지는지의 유일한 설명**이다.
자물쇠 그림만 두지 않고 글자를 함께 둔다(표준: 색·아이콘만으로 말하지 않는다).

### 한 자리에 한 가지 일만

승인된 자료에 「제출」 버튼을 띄워 두면 **눌러 보고 400 을 받는다.**
그 자리에 오는 것은 「수정 요청」이다. 잠긴 자료에는 둘 다 안 뜬다.

### 「승인」과 「허락」은 **다른 말**이다

같은 결재함, 같은 버튼 자리인데 되는 일이 완전히 다르다 —
문서에 도장을 찍는 것과 「고쳐도 된다」고 허락하는 것.
같은 글자를 돌려 쓰면 결재자가 **무엇에 도장을 찍는지 흐려진다.**
목록·상세·버튼·확인창 넷 다 갈라 적었다(승인/허락, 반려/거절).

### 확인창이 **되는 일**을 말한다

| 무엇 | 문구의 핵심 |
|---|---|
| 결재 승인 | 「같은 팀에 바로 공유됩니다」 (P6 그대로) |
| **수정 허락** | 「**승인본은 안 바뀝니다.** … 다시 승인을 받아야 교체됩니다」 |
| **수정 거절** | 「자료는 **승인된 채로 그대로** 남고 작성자는 고칠 수 없습니다」 |
| **수정 그만두기** | 「**고친 내용은 지워지지 않습니다** — 승인본에 반영되지 않을 뿐」 |
| 수정 요청(자료 목록) | 「**팀이 보는 화면은 지금 그대로입니다**」 ← 제출 창과 정반대의 말 |

제출 창은 「지금 이 문서가 그대로 **얼어붙습니다**」라고 말한다.
수정 요청은 **아무것도 안 얼린다** — 두 창이 같은 말을 하면 안 된다.

### 수정 요청은 **문서가 아니다** — 빈 뷰어를 안 띄운다

결재함 상세에서 갈리는 지점을 `isRevision` **한 줄**에 모았다.
갈래를 흩어 두면 어느 한 곳이 반드시 「문서인 척」 그린다.
수정 요청에는 슬라이드 뷰어 대신 **무엇을 정하는 자리인지** 적고,
「3번 슬라이드 의견」 같은 빈 칸도 띄우지 않는다(슬라이드가 없으니까).

### 서버 쪽에서 하나 더 고쳤다 — 403 이 이유를 삼켰다

실제 앱 왕복에서 잡혔다. 잠금이 권한 판정 안에 들어 있어서(`decide` 의 SUBMIT 규칙)
승인본 재제출이 **403 「권한이 없습니다」**로 떨어졌다 —
맞는 말이지만 **제 자료를 낸 사람은 「내 자료인데 왜 권한이 없지」에서 멈춘다.**

`submit_block_reason()` 을 만들어 **이유를 한 곳에서만** 말하게 하고,
라우터가 **볼 수 있는 내 자료**일 때만 그걸 물어 400 + 사람 말로 거절한다.
남의 자료는 여전히 403 이고 **이유를 안 알려준다** — 상태를 말해 주면
남의 자료가 지금 어떤 상태인지가 새어 나간다.

### 먼저 한 일 — **P2 부터 누락이던 게이트 둘을 실제로 돌렸다**

여섯 단계 내내 「장치 VM 에 브라우저·rollup 이 없다」는 이유로 `npm run build` 와
`npm run e2e:all` 을 한 번도 안 돌렸다. 이번에 방법을 찾아 둘 다 돌렸다.

- **`npm run build`** — 저장소의 `node_modules` 는 macOS 에서 설치된 것이라
  rollup·esbuild 의 네이티브 바이너리가 리눅스에서 안 맞는다.
  **저장소를 건드리지 않고** 리눅스용 바이너리를 장치 VM 의 개인 폴더에 따로 받아
  `NODE_PATH` · `ESBUILD_BINARY_PATH` 로만 가리켰다. → **1,864 모듈 통과.**
- **`npm run e2e:all`** — 크로미움은 장치 VM 에 못 받는다(egress 차단, 이전 기록대로).
  대신 `dist/` 와 `e2e/` 만 클라우드 컨테이너로 옮겨 거기 있는 크로미움으로 돌렸다.
  스위트가 이미 `PW_CHROME` 환경변수를 읽게 되어 있어 **저장소는 안 고쳤다.**

### 그리고 **여섯 중 다섯이 죽어 있었다**

돌려 보니 통과한 스위트가 하나뿐이었다. 원인 셋 다 **브라우저 없이 잡을 수 있는 고장**이었다.
