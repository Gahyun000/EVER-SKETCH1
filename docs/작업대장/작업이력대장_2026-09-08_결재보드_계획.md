# 작업이력대장 - 결재 상태 보드(노션식) 계획

- [x] 년월일: 2026-09-08
- [x] 요청내용: 노션의 「시작 전 → 진행 중 → 완료」처럼 자료를 칸으로 나누고, 칸 사이로 옮기고 싶다. 반려·승인을 갈라 놓고 싶다.

## 0. 노션과 결정적으로 다른 점 하나

노션에서 카드를 끌면 **그 동작이 상태를 정합니다.** 칸이 원인이고 상태가 결과입니다.

여기서는 **반대**입니다.

```
결재 이력(Approvals)  →  derive()  →  자료의 상태
     ↑ 진실은 여기                        ↑ 이건 결과다. 저장돼 있지도 않다
```

`server/doc_state.py` 는 **최신 결재 행 하나**에서 상태를 계산합니다. 어디에도 「상태」라는
칸이 저장돼 있지 않습니다. 그래서 **카드를 끌어서 상태를 「정할」 수는 없습니다.**

끌기는 상태를 바꾸는 게 아니라 **일을 하는 것**이어야 합니다 — 제출한다, 거둔다, 승인한다.
그 일이 성공하면 이력이 한 줄 늘고, 그 결과로 상태가 바뀌고, 그제야 카드가 옮겨집니다.

**이 차이를 지키면** 보드는 편해지기만 합니다.
**안 지키면** 화면이 카드를 옮겨 놨는데 서버는 안 바뀐 상태가 생깁니다 —
새로고침하면 카드가 제자리로 돌아가고, 쓰는 사람은 무엇이 참인지 모릅니다.

---

## 1. 그래서 규칙 하나를 먼저 세웁니다

> **카드는 놓은 자리에 있어야 한다.**

놓은 자리와 다른 데로 가면 보드가 거짓말을 합니다.
그래서 **끌 수 있는 것은 「놓은 자리로 실제로 가는」 전이뿐**입니다.

이 규칙으로 걸러 보면, 끌 수 있는 것이 생각보다 적습니다. 그게 정확합니다.

### 걸러진 예 — 「승인 → 고칠 것」

승인된 자료를 「고칠 것」 칸으로 끌면 어떻게 될까요.
`수정 요청`은 **관리자 허락이 있어야** 고칠 수 있게 됩니다. 그래서 카드는
「고칠 것」이 아니라 **「기다리는 중」으로 갑니다** — 놓은 자리가 아닙니다.

→ **이 끌기는 막습니다.** 지금 있는 「수정 요청」 버튼을 그대로 씁니다.

---

## 2. 칸을 어떻게 나눌까

지금 상태는 여섯입니다: `draft · pending · rejected · approved · revision_pending · revising`

### ㄱ · 넷 (말씀하신 것에 가장 가까움)

| 칸 | 담기는 상태 | 누구 차례 |
|---|---|---|
| **쓰는 중** | draft | 나 |
| **기다리는 중** | pending · revision_pending | 관리자 |
| **고칠 것** | rejected · revising | 나 |
| **승인** | approved | — (팀이 보는 중) |

「고칠 것」 안에서 **반려**와 **수정 중**은 칩으로 가릅니다.
둘 다 「내가 손대야 움직인다」는 점에서 같은 일이라 한 칸에 둡니다.

### ㄴ · 다섯 (상태 이름 그대로)

쓰는 중 / 결재 중 / **반려** / **수정 중** / 승인 — 상태와 칸이 일대일.
대신 **수정 중은 드뭅니다.** 늘 비어 있는 칸이 하나 생깁니다.

**ㄱ을 권합니다.** 칸 이름을 「무엇이 일어났나」가 아니라 **「누가 무엇을 해야 하나」**로 두면,
화면을 보는 사람이 자기 할 일을 바로 압니다. 그게 노션 보드가 실제로 해 주는 일입니다.

---

## 3. 무엇을 끌 수 있나 — 보드는 둘입니다

### 작성자(L2)의 「내 자료」 보드

| 끌기 | 실제로 하는 일 | 있는 API |
|---|---|---|
| 쓰는 중 → 기다리는 중 | **제출** | `apiRequestApproval` |
| 고칠 것 → 기다리는 중 | **다시 제출** | 같은 것 |
| 기다리는 중 → 쓰는 중 | **거두기** | `apiWithdraw` |
| → **승인** | **못 끕니다** | 관리자가 정합니다 |

**끌 수 있는 것은 셋뿐입니다.** 「승인」 칸은 **놓을 수 없는 칸**으로 그립니다 —
회색으로 두고 「관리자가 정합니다」라고 적습니다. 안 그러면 끌어 놓고 왜 안 되는지 모릅니다.

### 관리자의 「결재함」 보드

| 끌기 | 하는 일 | 있는 API |
|---|---|---|
| 기다리는 중 → 승인 | **승인** | `apiDecide('approve')` |
| 기다리는 중 → 고칠 것 | **반려** | `apiDecide('reject')` |

둘 다 놓은 자리로 그대로 갑니다.

**결재함은 이미 보드에 가깝습니다** — 대기 / 승인 / 반려 / 거둠 탭이 있습니다.
탭을 칸으로 펴는 일에 가깝습니다.

---

## 4. 지킬 것

1. **끌기는 확인창을 거칩니다.**
   노션에서 카드를 끄는 건 가볍습니다. 여기서 「제출」은 **문서를 얼립니다** —
   되돌릴 수 없고, 낸 자료는 지울 수도 없게 됩니다.
   가벼운 동작에 무거운 일을 붙이면 사고가 납니다. 이미 만들어 둔 확인창을 그대로 씁니다.

2. **제출은 저장부터.** B에서 배운 그대로입니다. 결재본은 **서버에 저장된 문서**를 얼립니다.

3. **미리 옮기지 않습니다.** 화면이 카드를 먼저 옮겨 놓고 나중에 맞추면(낙관적 갱신),
   실패했을 때 화면과 서버가 어긋납니다. **서버가 답한 뒤에** 옮깁니다.
   끄는 동안에는 카드를 흐리게 두고 「보내는 중」이라고 적습니다.

4. **상태는 화면이 계산하지 않습니다.** `/api/approvals/status-map` 의 `state` 를 그대로 씁니다 —
   목록 화면이 이미 부르는 그것입니다. **서버는 한 줄도 안 고칩니다.**

5. **끌기만이 유일한 길이면 안 됩니다.** 마우스로 끌 수 없는 사람이 있고, 좁은 화면도 있습니다.
   지금 있는 버튼(✈ 제출 · 수정 요청)을 **그대로 둡니다.** 끌기는 빠른 길이지 유일한 길이 아닙니다.

6. **잠긴 자료는 안 끌립니다.** `status-map` 이 `locked` 를 이미 줍니다.

---

## 5. 어디에 놓을까

지금 「내 자료」에는 폴더 · 검색 · 날짜 범위 · 쪽 번호가 붙어 있습니다.
보드로 **바꾸는 게 아니라** 보기를 하나 **더하는** 쪽입니다.

```
[ 목록 ] [ 보드 ]      ← 보기 전환. 지금 목록은 그대로 둔다.
```

**범위는 목록과 같게 합니다.** 지금 규칙이 「목록은 한 단계만, 검색은 하위 전부」(D27)인데,
보드가 세 번째 규칙을 만들면 사람이 「보드는 어디까지 보이지?」를 또 외워야 합니다.

## 6. 만들 것

| 조각 | 새로 만드나 |
|---|---|
| 서버 | **아무것도 안 고침** — 전이 API가 다 있다 |
| 상태 읽기 | `/status-map` 그대로 |
| **전이 규칙** | **새로** — 순수 함수 |
| 보드 화면 | 새로 |
| 끌기 | 새로 |
| 확인창 | 있는 것(`ui/Modal`) 재사용 |
| 버튼 | 그대로 둠 |

### 전이 규칙을 순수 함수로 빼는 이유

```
moveIntent(from, to, role, mine, locked)
  → { do: '제출' | '다시 제출' | '거두기' | '승인' | '반려', api }   // 할 수 있다
  → { no: '관리자가 정합니다' }                                      // 못 한다 + 이유
```

화면과 떨어져 있으면 `node` 로 바로 시험할 수 있습니다 —
`unfilled.ts` 와 같은 방식입니다. 그리고 **「못 한다」에 이유가 반드시 붙습니다.**
이유 없는 거절은 「고장 났다」로 읽힙니다.

## 7. 위험

| 위험 | 왜 | 대응 |
|---|---|---|
| 실수로 제출된다 | 노션 습관으로 가볍게 끈다 | 확인창 필수. 「얼어붙습니다」를 그 자리에 |
| 화면과 서버가 어긋난다 | 미리 옮겨 놓으면 | 서버 답 뒤에 옮긴다 |
| 못 끄는 이유를 모른다 | 그냥 안 움직이면 | 「승인」 칸은 처음부터 놓을 수 없게 그린다 |
| 반려 사유가 없다 | `status-map` 에 `decision_message` 가 없다 | **착수계획의 B-1과 같은 문제.** 같이 푼다 |
| 끌기가 유일한 길이 된다 | 버튼을 지우면 | 버튼을 그대로 둔다 |

**반려 사유는 여기서 특히 아쉽습니다.** 보드에서 「고칠 것」 칸에 카드가 있는데
**왜 반려됐는지 그 자리에 없으면** 결국 결재함을 열어야 합니다 —
보드를 만든 이유가 반쯤 사라집니다.

---

## 8. 순서

```
1. 전이 규칙 순수 함수 + 검사      ← 여기가 제일 중요하다
2. 작성자 보드 (읽기만 — 칸에 나눠 보여주기)
3. 끌기 + 확인창
4. 관리자 보드(결재함) — 탭을 칸으로
5. 반려 사유 (B-1과 함께)
```

**2를 먼저 따로 냅니다.** 끌기 없이 나눠 보여 주기만 해도 「반려와 승인을 갈라 보고 싶다」는
말씀은 이미 이뤄집니다. 끌기는 그다음에 얹습니다 — 그게 위험한 부분이라 따로 봐야 합니다.
