# 작업이력대장 - 결재 상태 보드 계획 (v2 — 끌기 없음)

- [x] 년월일: 2026-09-08
- [x] 요청내용: 노션처럼 상태별로 칸을 나누고, **반려된 자료가 승인되면 반려 칸에서 승인 칸으로 옮겨져 있게** 한다.
- [x] 상태: **계획만.** 코드는 손대지 않았다.
- [x] v1 과 다른 점: **끌기를 뺀다.** 카드를 옮기는 것은 사람이 아니라 **결재 결과**다.

---

## 0. v1 이 왜 틀렸나

앞 계획은 「카드를 끌면 그 일이 일어난다」로 짰습니다. 그래서 절반이
**끌기를 어떻게 안전하게 만들 것인가**였습니다 — 확인창, 놓을 수 없는 칸,
미리 옮기지 않기, 놓은 자리와 실제 도착지가 다른 경우.

**그게 필요 없습니다.** 카드는 **결재가 나면 저절로 옮겨져 있으면** 됩니다.
관리자가 승인하면, 다음에 볼 때 그 자료는 승인 칸에 있습니다.

그러면 이 기능은 **읽기 전용 보기 하나**가 됩니다.

| v1 에서 걱정하던 것 | v2 |
|---|---|
| 실수로 제출된다 | **없음** — 끌기가 없다 |
| 놓은 자리와 도착지가 다르다 | **없음** |
| 미리 옮겼다가 서버와 어긋난다 | **없음** — 서버가 말한 대로만 그린다 |
| 「승인」 칸을 못 놓게 그려야 한다 | **없음** |
| 끌기가 유일한 길이 된다 | **없음** — 버튼은 그대로 |
| 전이 규칙 순수 함수 | **없음** — 전이를 화면이 안 한다 |

**서버도 안 고치고, 되돌릴 수 없는 일도 안 만듭니다.**
남는 것은 「같은 자료를 어떻게 묶어 보여줄까」 하나입니다.

## 1. 칸을 어떻게 나눌까

지금 상태는 여섯입니다.

```
draft            아직 안 냄
pending          냈고 관리자 답 기다림
revision_pending 수정 요청 냈고 허락 기다림
rejected         반려됨 — 내가 고쳐야 함
revising         수정 허락 받음 — 내가 고쳐야 함
approved         승인 — 팀이 보는 중
```

여섯을 그대로 칸으로 두면 **여섯 칸**입니다. 그중 둘(`revision_pending`·`revising`)은 드물어서
거의 늘 비어 있습니다.

### 노션도 여러 상태를 한 칸에 묶습니다

보내 주신 두 번째 그림이 그 증거입니다 — 상태 목록이 이렇게 묶여 있습니다.

```
할 일    ← 계획 중 · 보류      (두 상태가 한 묶음)
진행 중  ← 진행 중
완료     ← 완료
```

같은 방식으로 넷이면 충분합니다.

| 칸 | 담기는 상태 | 칩으로 가름 |
|---|---|---|
| **쓰는 중** | draft | — |
| **기다리는 중** | pending · revision_pending | 「결재 중」 · 「수정 요청 중」 |
| **고칠 것** | rejected · revising | 「반려」 · 「수정 중」 |
| **승인** | approved | — |

**말씀하신 「반려 → 승인」이 이 안에서 그대로 보입니다** — 반려된 자료는 「고칠 것」에 있다가,
다시 내면 「기다리는 중」으로, 승인되면 「승인」으로 옮겨져 있습니다.

- **ㄱ · 넷** (위 표) — 빈 칸이 안 생긴다. 칩으로 가른다.
- **ㄴ · 여섯** — 상태와 칸이 일대일. 대신 두 칸은 거의 늘 「0」.
  (노션도 「보류 0」을 그냥 두긴 합니다 — 보내 주신 그림에 있습니다)

**ㄱ을 권합니다.** 다만 「반려」와 「수정 중」을 굳이 갈라 보고 싶으시면 ㄴ도 괜찮습니다 —
끌기가 없어지면서 **칸을 늘리는 비용이 거의 사라졌습니다.**

## 2. 새로 생긴 진짜 질문 — 카드는 **언제** 옮겨지나

끌기가 없어지니 이게 유일하게 어려운 질문이 됩니다.

**관리자가 승인해도 내 화면은 모릅니다.** 지금 `/api/approvals/status-map` 은
라이브러리 화면에 **들어올 때** 한 번 부릅니다. 보드를 켜 놓고 있으면 카드는 그대로입니다.

| 안 | 언제 다시 읽나 | 비용 |
|---|---|---|
| **ㄱ** | 화면에 들어올 때만 (지금과 같음) | 0. 대신 켜 둔 채로는 안 바뀜 |
| **ㄴ** | **창을 다시 볼 때** 다시 읽는다 | 거의 0. 다른 탭 갔다 오면 최신 |
| ㄷ | 60초마다 | 요청이 계속 나감 |
| ㄹ | 실시간(SSE) | **서버 작업** |

**ㄴ을 권합니다.** `visibilitychange` 한 줄입니다. 결재는 몇 분·몇 시간 단위로 일어나는 일이라
실시간이 필요 없고, 사람은 대개 **다른 걸 하다 돌아와서** 봅니다.

### 그리고 「내가 없는 사이에 바뀐 것」을 알려야 합니다

노션은 내가 끌어서 옮기니 옮긴 걸 압니다. 여기서는 **남이 바꿉니다.**
그래서 「3일 전에 승인됐는데 몰랐다」가 생깁니다.

- 각 칸에 **건수**를 답니다 (「고칠 것 2」) — 결재함 배지와 같은 방식.
- 카드에 **언제 그렇게 됐는지**를 적습니다 (「어제 반려」·「9/1 승인」).
  `status-map` 이 `decided_at` 을 이미 줍니다. **서버 안 고칩니다.**

## 3. 폴더를 어떻게 할까

지금 목록은 **폴더 안**을 봅니다. 보드도 폴더 안만 보면
「내 반려 자료가 어디 있든 다 보여줘」가 안 됩니다 — **그게 보드를 쓰는 이유인데** 말이죠.

**보드는 검색과 같은 범위를 씁니다** — 하위 폴더까지 전부.
지금 규칙이 「목록은 한 단계만, 검색은 하위 전부」(D27)라, 보드를 검색 쪽에 붙이면
**규칙이 안 늘어납니다.** 대신 카드에 **폴더 이름**을 적습니다 — 어디 있는 자료인지 알아야 하니까요.

## 4. 만들 것

| 조각 | 새로 만드나 |
|---|---|
| 서버 | **아무것도 안 고침** |
| 상태 읽기 | `/status-map` 그대로 (목록이 이미 부른다) |
| **상태 → 칸** | **새로** — 순수 함수. 여섯 상태를 네 칸으로 |
| 보드 화면 | 새로 — 칸 넷 · 카드 · 건수 |
| 다시 읽기 | `visibilitychange` 한 줄 |
| 보기 전환 | `[목록] [보드]` |
| 끌기 · 확인창 · 전이 | **없음** |

### 순수 함수 하나

```
columnOf(state) → '쓰는 중' | '기다리는 중' | '고칠 것' | '승인'
```

한 줄짜리지만 **여섯 상태를 하나도 안 빠뜨렸는지**가 중요합니다.
새 상태가 생기는 날 조용히 사라지는 카드가 없도록,
**여섯 개를 다 세는 검사**를 같이 둡니다 — `node` 로 바로 돌아갑니다.

---

## 5. 남는 위험 — 둘뿐입니다

| 위험 | 왜 | 대응 |
|---|---|---|
| **상태 하나가 어느 칸에도 안 들어간다** | 나중에 상태가 늘면 | 여섯을 다 세는 검사. 모르는 상태는 「쓰는 중」으로 두고 **눈에 띄게 표시** |
| **반려 사유가 없다** | `status-map` 에 `decision_message` 가 없다 | 착수계획 B-1 과 **같은 문제** |

**반려 사유가 여기서 제일 아쉽습니다.** 「고칠 것」 칸에 카드가 있는데
**왜 반려됐는지 그 자리에 없으면** 결국 결재함을 열어야 합니다.
보드를 만든 이유가 반쯤 사라집니다. **B-1 과 한 번에 푸는 게 맞습니다.**

## 6. 순서

```
1. 상태 → 칸 순수 함수 + 검사        (작다)
2. 보드 화면 · 보기 전환             ← 여기까지가 「반려/승인 갈라 보기」
3. 창 다시 볼 때 갱신 · 언제 바뀌었는지
4. 반려 사유 (B-1 과 함께)
```

**1~2 만으로 말씀하신 것이 됩니다.** 3·4 는 그 뒤에 얹습니다.

## 8. 앞 계획들과의 관계

- **착수계획 B-1(반려 사유)** — 여기서도 필요합니다. **한 번에 풉니다.**
- **셸(D)** — 보드는 「내 자료」의 한 보기라 셸이 없어도 됩니다. **순서를 안 묶습니다.**

  그 항목은 여기로 합칩니다.

그리고 v1 계획서(`작업이력대장_2026-09-08_결재보드_계획.md`)는 **이 문서로 대체됩니다.**
