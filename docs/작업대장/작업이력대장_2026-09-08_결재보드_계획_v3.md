# 작업이력대장 - 결재 상태 보드 계획 (v3 — 역할별 기준)

- [x] 년월일: 2026-09-08
- [x] v2 와 다른 점: **칸의 기준이 역할마다 다르다**는 지적을 반영한다.
- [x] 상태: **계획만.**

---

## 0. 지적이 맞습니다 — 그런데 「역할별」이 아니라 「화면별」로 갈립니다

v2 의 칸 넷(쓰는 중 / 기다리는 중 / 고칠 것 / 승인)은 **「내 차례인가」**를 기준으로 잡은 것입니다.
그 기준은 **자기가 쓴 자료**에만 맞습니다.

관리자가 결재함에서 보는 것은 **남이 낸 자료**입니다. 거기서 「기다리는 중」은
**내가 결정해야 할 것**이고, 「고칠 것」은 **상대가 고칠 차례**입니다 — **뜻이 뒤집힙니다.**

그런데 이건 「역할에 따라 칸 이름을 바꾼다」로 풀 일이 아닙니다.
**이미 화면이 나뉘어 있기 때문입니다.**

```
내 자료    ← 내가 쓴 것          기준: 「내 차례인가」
결재함     ← 남이 낸 것(관리자)   기준: 「내가 결정할 것인가」
팀 공유    ← 승인본              기준: 없음 — 전부 승인이다
```

**보드는 셋이 아니라 둘입니다.** 역할은 「어느 화면을 갖는가」만 정합니다.

---

## 1. 화면별 칸

### 「내 자료」 보드 — L2 · L1 공통

관리자도 자기 자료를 씁니다(지금 데이터베이스에도 admin 소유 자료가 있습니다).
자기가 쓴 것을 볼 때는 **역할이 달라도 묻는 것이 같습니다.**

| 칸 | 상태 |
|---|---|
| 쓰는 중 | draft |
| 기다리는 중 | pending · revision_pending |
| 고칠 것 | rejected · revising |
| 승인 | approved |

### 「결재함」 보드 — L1 관리자

**「쓰는 중」 칸이 없습니다.** 낸 적 없는 자료는 결재함에 오지 않습니다.
그리고 나머지 칸의 뜻이 뒤집힙니다.

| 칸 | 상태 | 내 자료 보드에서는 |
|---|---|---|
| **결정할 것** | pending · revision_pending | 「기다리는 중」이던 것 |
| **낸 사람 차례** | rejected · revising | 「고칠 것」이던 것 |
| 승인 | approved | 같음 |
| 거둠 | withdrawn | (「쓰는 중」으로 돌아감) |

**같은 자료가 두 보드에서 다른 칸에 있습니다.** 그게 맞습니다 —
내가 낸 것은 내가 기다리는 중이고, 관리자에게는 결정할 것입니다.

### 「결재함」 보드 — L2 작성자

결재함은 작성자에게도 있습니다(「내가 낸 결재」). 그런데 거기 있는 것은
**내 자료 보드의 부분집합**입니다 — 낸 적 있는 것만.

**여기엔 보드를 안 넣습니다.** 같은 것을 두 군데서 다르게 묶으면
「어느 쪽이 맞지」가 생깁니다. 작성자는 「내 자료」 보드 하나면 됩니다.

### 「팀 공유」 — L3 열람자 포함

`team_library.py` 가 보여 주는 것은 **`Approvals[승인].snapshot`** 뿐입니다.
**전부 승인본입니다.** 상태로 나눌 것이 없습니다 — 한 칸짜리 보드가 됩니다.

**보드를 안 넣습니다.**

### 열람자(L3)의 「개인 스케치」

열람자는 결재를 내지 않습니다(D13). 그래서 그 자료들은 **전부 `draft`** 입니다.
역시 한 칸짜리입니다. **보드를 안 넣습니다.**

## 2. 그래서 누가 무엇을 보나

| | 내 자료 보드 | 결재함 보드 | 팀 공유 |
|---|---|---|---|
| **L1 관리자** | ○ (내 차례 기준) | ○ (결정 기준) | 보드 없음 |
| **L2 작성자** | ○ (내 차례 기준) | — (내 자료 보드가 대신) | 보드 없음 |
| **L3 열람자** | — (전부 draft) | 없음 | 보드 없음 |

**열람자에게는 보드가 아예 없습니다.** 억지로 주면 한 칸짜리가 되고,
「왜 칸이 하나지」를 설명해야 합니다. 없는 게 정직합니다.

> **다만 열람자·팀 공유에도 묶어 보고 싶은 축은 있습니다** — 달(2026-10)이나 사람별.
> 그건 상태 보드가 아니라 **다른 기능**입니다. 여기서 다루지 않습니다.

## 3. 이 갈래가 만들어 내는 것

### 순수 함수가 하나에서 둘로

```
columnOfMine(state)  → '쓰는 중' | '기다리는 중' | '고칠 것' | '승인'
columnOfInbox(state) → '결정할 것' | '낸 사람 차례' | '승인' | '거둠'
```

둘 다 **여섯(일곱) 상태를 하나도 안 빠뜨렸는지**를 검사합니다.
그리고 **둘이 같은 상태를 다르게 부른다는 사실 자체**를 검사에 적어 둡니다 —
나중에 누가 「둘을 합치자」고 할 때 왜 갈랐는지 알 수 있게.

### 결재함은 이미 절반쯤 보드입니다

지금 결재함에 **대기 / 승인 / 반려 / 거둠 탭**이 있습니다(`STATUS_ORDER`).
그건 **`status` 기준**이고, 보드는 **`doc_state` 기준**입니다 — 미묘하게 다릅니다.

- `status` = 결재 행 하나의 상태
- `doc_state` = 그 자료의 상태 (수정 요청이 걸리면 달라진다)

**보드는 `doc_state` 를 씁니다.** 자료 목록의 칩이 이미 그렇게 하고 있고
(「`status` 만 보면 수정 요청이 걸린 자료가 '승인'이라고 적히면서 실제로는 '수정 중'이다」),
보드에서 같은 실수를 반복할 이유가 없습니다.

**그래서 결재함 보드는 탭을 그대로 칸으로 펴는 게 아닙니다.** 기준이 바뀝니다.

## 4. 순서 — 다시

```
1. columnOfMine + 검사                 (작다)
2. 「내 자료」 보드 · 보기 전환          ← 여기까지가 말씀하신 「반려/승인 갈라 보기」
3. 창 다시 볼 때 갱신 · 언제 바뀌었는지
4. 반려 사유 (착수계획 B-1 과 함께)
5. columnOfInbox + 결재함 보드          ← 관리자 쪽. 기준이 다르니 따로
```

**1~2 로 충분히 쓸 만해집니다.** 5 는 그 뒤에 따로 봅니다 —
기준이 다른 보드를 같이 만들면 둘이 섞입니다.

## 6. 짚어 둘 것 하나

이 지적으로 **v2 가 조용히 틀릴 뻔한 것**을 하나 막았습니다.

v2 대로 「칸 넷」을 만들고 그걸 결재함에도 그대로 썼다면,
관리자는 **자기가 결정해야 할 자료를 「기다리는 중」 칸에서** 보게 됩니다.
관리자에게 그건 기다리는 것이 아니라 **할 일**입니다.

칸 이름 하나가 「누가 움직여야 하는가」를 반대로 말하는 셈이고,
그건 보드를 만든 이유를 정면으로 어깁니다.
