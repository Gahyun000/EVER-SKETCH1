0. 지금은 어떻게 되어 있나

상황지금 벌어지는 일
아이디가 겹칠 때 다 채우고 「가입 신청」을 눌러야 「이미 사용 중인 아이디입니다」가 뜬다. 비밀번호·이름·부서를 다 친 뒤에 처음부터 다시 고민하게 된다.
아이디 형식이 틀릴 때 마찬가지로 눌러야 안다. 규칙(영문 소문자·숫자·. _ -, 3~32자)이 화면 어디에도 안 적혀 있다. 「사내 아이디」라고만 되어 있다.
비밀번호 오타 확인칸이 없다. 오타가 나면 본인도 모른 채 가입이 되고, 로그인할 때 비로소 막힌다. 이 제품에는 비밀번호 찾기가 없어서 그때부터는 관리자가 초기화해 줘야 들어올 수 있다.
같은 제품 안에서 규칙이 갈려 있습니다. 「비밀번호 변경」 화면에는 이미 「새 비밀번호 확인」 칸이 있습니다(ChangePasswordForm.tsx). 비밀번호를 두 번 받는 곳과 한 번만 받는 곳이 나뉘어 있는데, 더 위험한 쪽이 한 번만 받는 가입 화면입니다 — 변경은 실패해도 옛 비밀번호로 들어오지만, 가입은 실패하면 들어올 방법이 없습니다.

㉯를 권하는 이유는 「편해서」가 아니라 「틀릴 자리가 없어서」입니다. ㉮에는 「확인은 했는데 그 뒤에 아이디를 고친」 상태가 존재합니다. 이 상태를 무효로 되돌리는 코드를 빠뜨리면 중복된 아이디로 가입 버튼이 켜집니다 — 서버가 다시 막아 주긴 하지만, 그때 사용자가 보는 건 "확인까지 했는데 왜 안 되지"입니다. ㉯에는 그 상태 자체가 없습니다. 문제를 표시로 막지 않고 구조에서 없앱니다. (폴더 네비게이션 때 … 를 없앤 것과 같은 판단입니다.)

어느 안을 고르든 같이 넣을 것 — 형식 규칙을 미리 말해 준다

지금은 규칙이 화면에 없어서 서버에 물어봐야만 틀린 걸 압니다. 형식은 서버에 묻지 않고도 판정할 수 있으니, 대문자나 한글을 치는 순간 바로 말해 줍니다. 서버 호출은 형식이 맞은 다음에만 나갑니다.

2. 아이디 중복 확인의 보안 문제 — 짚고 넘어가야 합니다

중복 확인 기능은 「그 아이디가 존재하는가」를 아무나 물어볼 수 있게 만듭니다. 이 제품은 지금 그 반대로 설계돼 있습니다 — 로그인이 실패하면 「아이디 또는 비밀번호가 올바르지 않습니다」라고만 답합니다. 어느 쪽이 틀렸는지 알려주면 계정 존재 여부가 새어 나가기 때문입니다. 자료 조회도 404 와 403 을 일부러 통일해 두었습니다(authdeps.require_project).
그런데 이미 새고 있습니다. 지금도 가입 폼에 아이디를 넣고 「가입 신청」을 누르면 「이미 사용 중인 아이디입니다」가 그대로 나옵니다. 즉 중복 확인 API 는 없던 구멍을 새로 뚫는 게 아니라, 이미 있는 구멍을 빠르게 만듭니다.

그래서 막을 것은 「알려주는 것」이 아니라 「빠르게 많이 묻는 것」입니다:
· 같은 IP 에서 분당 20회까지만 (넘으면 잠시 거절)
· 응답은 「쓸 수 있음 / 쓸 수 없음」 두 가지뿐 — 이미 있는 아이디인지, 못 쓰는 형식인지 나누지 않는다
· 감사로그에 남긴다(이미 AuditLogs 가 있습니다)

사내망 전용이고 아이디가 사내 아이디라 서로 이미 아는 사이라는 점도 근거입니다. 다만 이 판단은 제가 아니라 대표님이 하실 일이라 여기에 적어 둡니다 — "중복 확인은 넣지 말고 지금처럼 가입 눌렀을 때만 알려줘"도 충분히 합리적인 선택입니다.
