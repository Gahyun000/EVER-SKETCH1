## 0. 한 줄 요약

**관리자가 밀어주는 축(회차·배부)을 걷어내고, 개인이 만들어 올리는 축(폴더·결재)으로 갈아탄다.**
표준 양식은 배부의 부속품에서 **독립된 생성 옵션**으로 승격한다.
승인은 자료가 팀에 공개되는 **유일한 관문**이며, 승인되는 순간 자동으로 공유된다.

```
[지금]  관리자가 회차를 열고 → 전원에게 1장씩 배부 → 작성 → 취합
[이후]  개인이 표준양식/빈슬라이드를 골라 만들고 → L1에게 제출 → 승인 → 팀에 자동 공유
```

## 2. 조사에서 나온 결정적 사실

1. **표준 양식은 이미 독립돼 있다.**
   `server/template_seed.py`는 서버 내 어떤 모듈도 import하지 않는 순수 함수 모듈이고,
   프런트 `src/template/slots.ts`도 `src/cycles/*`와 import가 **한 줄도 없다.**
   회차와의 결합은 오직 호출자 두 곳 — `cycles.py:236 distribute()`, `routes_cycles.py:390 preview`.

2. **표준 양식이 나오는 통로가 회차 API 두 개뿐이다.**
   `POST /api/cycles/{cid}/distribute`, `GET /api/cycles/{cid}/preview`. 둘 다 `cid`를 요구한다.
   **진입점을 먼저 만들지 않고 회차를 지우면 표준 양식이 죽는다.** 이번 작업의 유일한 필수 신규 코드.

3. **`Templates` 테이블은 죽은 코드다.** 회차 개설 때 굽기만 하고 배부는 이걸 읽지 않는다
   (`build_template_state()`를 다시 호출한다). `slot_policy` 컬럼을 읽는 코드도 없다. 통째로 버려도 된다.

4. **`pptx_import.py:28`이 `template_seed`를 역참조한다**(`PAGE_W`, `PAGE_H`). 삭제 금지.

5. **승인 개념이 이미 둘 있다.** `Projects.submit_status` vs `Approvals.status`.
   그대로 얹으면 한 자료에 승인 상태가 두 개 생긴다. `Approvals` 하나로 정리한다.

6. **D3(L3 순수 열람자) 덕분에 기존 권한 계약이 대부분 살아남는다.**
   `test_열람자는_편집_삭제_불가`, `test_열람자는_메모를_읽지도_쓰지도_못한다`는 그대로 통과한다.
   바뀌는 건 `test_열람자는_발행본만_읽는다` 하나 — 기준이 `published` → `팀 승인본`으로 옮겨간다.

## 3. 목표 개념 모델

### 3.1 핵심 아이디어 — 승인본과 작업본의 분리

> **팀이 보는 것은 `Projects`가 아니라 `Approvals.snapshot`이다.**

`ebook_html1`의 결재는 요청 시점에 `Projects.state`를 통째로 얼려 `Approvals.snapshot`에 복사한다
(`server/approvals.py request()`). 이미지가 아니라 편집 가능한 페이지 JSON 그대로다.

이 구조가 D8("수정 중에 보던 자료가 사라지면 안 된다")을 **추가 장치 없이** 해결한다.

```
Projects.state            ← L2가 지금 고치는 살아 있는 문서 (요동친다)
Approvals[승인].snapshot  ← 얼어붙은 승인본 (팀이 보는 것, 절대 안 흔들림)
```

L2가 수정 중이어도 팀의 화면은 직전 승인본 그대로다. 재승인이 나야 교체된다.
「수정 중」 배지만 얹으면 보는 쪽도 "곧 바뀔 자료"임을 안다.

### 3.2 역할별로 보이는 것

```
┌─ L2 김가현 (A팀) ──────────────┐   ┌─ 팀 공유 (A팀) ─────────────────┐
│  내 폴더                        │   │  2026-09                        │
│   └ 2026 계획/                  │   │   ├ 김가현 · 3분기 로드맵 ✔     │
│      ├ 3분기 로드맵  [승인됨]───┼──>│   └ 홍길동 · 품질 이슈 ✔        │
│      ├ 초안 메모     [작성 중]  │   │  2026-08                        │
│      └ 실험용        [작성 중]  │   │   └ 김가현 · 상반기 결산 ✔      │
└────────────────────────────────┘   └─────────────────────────────────┘
  본인 + L1만 본다                     L1 · A팀 L2 · A팀 L3 이 본다
                                       B팀은 전혀 안 보인다
```

- **L2**: 자기 폴더(작업본 전부) + 팀 공유(같은 팀 승인본). 동료의 **작업 중인 것은 못 본다**
- **L3**: 팀 공유만. 개인 폴더 없음
- **L1**: 전부

### 3.3 팀 공유의 모양 (D5)

폴더 테이블을 쓰지 않는다. `Approvals` 중 `status='approved'`인 최신 행을 모아
**승인 연월로 그룹핑한 뷰**다. 사람이 위치를 고르는 단계가 없다 — 승인 즉시 제자리를 찾는다.

- 묶음 키 = 승인 시각(`decided_at`)의 `YYYY-MM`
- 한 프로젝트는 최신 승인본 1건만 노출. 과거 회차는 상세에서 이력으로 열람
- 재승인되면 새 묶음으로 이동한다 (9월 승인 → 10월 재승인 = 10월 묶음)

### 3.4 자료의 생애주기

```
                    ┌──────────────────────────────────────────┐
                    ↓                                          │
  [draft] ──제출──> [pending] ──반려──> [rejected] ──재제출─────┘
   편집O            편집X   │           편집O
   팀 X             팀 X    │           팀 X (첫 승인 전)
                           │
                         승인 ── 팀 공유에 자동 등장
                           ↓
                      [approved] ──────────────────────┐
                       편집X · 팀 O                     │
                           ↑                        수정 요청
                           │                            ↓
                        재승인                  [revision_pending]
                           │                    편집X · 팀 O(이전 승인본)
                           │                            │
                    [pending(새 round)] <──재제출──   L1 허락
                     편집X · 팀 O(이전 승인본)          ↓
                                                   [revising]
                                          편집O · 팀 O(이전 승인본) + 「수정 중」
```

**상태는 저장하지 않고 `Approvals` 최신 행에서 파생한다.** 진실이 한 곳에만 있게.

| 최신 결재 행 | 파생 상태 | L2 편집 | 팀에게 | 배지 |
|---|---|---|---|---|
| 없음 / withdrawn | `draft` | O | 안 보임 | — |
| `kind=approval, pending` | `pending` | X | 직전 승인본(있으면) | 결재 중 |
| `kind=approval, rejected` | `rejected` | O | 직전 승인본(있으면) | 반려 |
| `kind=approval, approved` | `approved` | X | **승인본** | — |
| `kind=revision, pending` | `revision_pending` | X | 승인본 | 수정 요청 중 |
| `kind=revision, approved` | `revising` | O | 승인본 | **수정 중** |

### 5.2 판정표

| 액션 | L1 관리자 | L2 작성자 | L3 열람자 |
|---|---|---|---|
| READ | 전부 | 본인 자료 + **같은 팀 승인본** | **같은 팀 승인본만** |
| WRITE | 전부 | 본인 AND `not locked` | **본인 개인 스케치만** (D13) |
| DELETE | 전부 | **결재 이력이 없을 때만** (D16) | 본인 것 · 결재 이력 없음 |
| `TEMPLATE_USE` | O | O | **X** | ← **P2에서 되살린다.** P1에서는 D3(L3 순수 열람자) 때문에 `WRITE` 와 언제나 같은 답을 내서 만들지 않았다. D13 이 D3 을 뒤집으면서 **L3 도 WRITE 는 되지만 표준 양식은 못 쓰는** 상태가 됐다 — 이제 두 액션이 갈린다 |
| `SUBMIT` | — (D15: 결재를 타지 않는다) | 본인 자료 | X |
| `SHARE` / `UNSHARE` | O — 스위치 (D15) | X (승인으로만) | X |
| `DECIDE` / `REVISION_DECIDE` | O — **단독 결재자** (D11) | X | X |
| `REVISION_REQUEST` | — | 본인 승인본 | X |
| `COMMENT_READ` / `WRITE` | 전부 | 본인 자료 | **X** |
| `AI_USE` | O | O | **X** |
| `TEAM_MANAGE` / `USER_MANAGE` / `SETTINGS_MANAGE` | O | X | X |

- `locked` = 파생 상태가 `pending` / `approved` / `revision_pending`
- `같은 팀` = `Approvals.team_id ∈ Actor.team_ids` (현재 소속 기준으로 승인 당시 팀을 조회)
- **L3 행이 기존 viewer 계약과 거의 같다.** WRITE·DELETE·COMMENT·AI 전부 X 그대로 (D3의 이득)
- **L1 행도 기존 계약 그대로다.** D11에 따라 `decide()`의 `if actor.role == ADMIN: return True` 를 손대지 않는다.

## 9. 실행 순서

각 단계는 **끝에서 전체 테스트가 초록**이어야 다음으로 넘어간다.

| 단계 | 내용 | 완료 판정 |
|---|---|---|
| **P0** | 작업 브랜치 · 현재 테스트 전량 통과 기준선 기록 · **기존 DB 백업 후 새 DB로 교체**(D10) | 관리자 시드 계정으로 앱이 뜬다 |
| **P1** | **표준 양식 독립** — `POST /api/projects/from-template` + 「새로 만들기」 선택 모달 + `due_label` 제거 | 회차를 거치지 않고 표준 양식 이북이 만들어진다 |
| **P1.5** | **계정 전환 시 상태 초기화** — 로그아웃·계정 변경 때 `useProjects`·`useBuilder`를 비우고 `booted` 가드를 계정별로 | 관리자로 보다가 작성자로 로그인하면 목록이 **다시 조회**된다. 편집 화면에서 로그아웃해도 다음 사람이 그 문서에 착지하지 않는다 |
| **P2** | **회차·배부 제거** — §8 삭제 목록 집행, `permissions.py` 회차 규칙 제거, 테이블 DROP · 컬럼 정리 | `test_template_*` 3종 여전히 통과. 앱이 회차 없이 뜬다 |
| **P3** | **팀** — `Teams`/`TeamMembers` + 팀 관리 화면 + `Actor.team_ids` | L1이 팀을 편성하고 L2·L3을 넣을 수 있다 |
| **P4** | **개인 폴더** — `Folders(owner_id)` + 폴더 탐색기 UI 이식 + `delete_folder` 가드 | 각자 자기 폴더 트리만 보인다. 남의 폴더명이 안 샌다 |
| **P5** | **결재 이식** — `approvals.py` + `routes_approvals.py` + `src/approvals/` + 셸 | L2 제출 → L1 승인/반려 + 슬라이드별 코멘트가 돈다 |
| **P6** | **팀 공유 + 가시성 전환** — `/api/team-library` 월별 뷰, `visible_project_filter` 교체 | 승인 즉시 같은 팀에 뜬다. 다른 팀은 목록에도 없다 |
| **P7** | **수정 요청 흐름** — `Approvals.kind='revision'` + 상태 파생 + 「수정 중」 배지 | L2 수정 중에도 팀 화면이 직전 승인본으로 안 흔들린다 |
| **P8** | 테스트·문서 정리 — 계약 테스트 재작성, e2e 재구성, `README.md`/`AGENTS.md`/`start_docs` 갱신 | 전량 초록 + 문서가 실제 코드와 일치 |

**순서 근거**
- P1이 P2보다 먼저인 이유: 표준 양식 진입점을 먼저 만들어야, 회차를 지우는 순간 표준 양식이 죽는 구간이 안 생긴다
- **P1.5가 P2보다 먼저인 이유**: 계정 간 유출은 회차와 무관한 별개 결함이고, P2를 하면 서버가 내려주는
  목록이 작아져 **증상이 옅어진다**. 3건이 1건으로 줄면 "가끔 이상한 게 보인다"가 되고, 그때는 원인을
  짚기가 훨씬 어렵다. 증상이 뚜렷할 때 잡는다
- P3(팀)이 P6(가시성)보다 먼저인 이유: "같은 팀 승인본"의 팀이 없으면 규칙을 쓸 수가 없다
- P5(결재)가 P6보다 먼저인 이유: 승인 개념이 있어야 승인본이 존재한다

## 10. 위험

| # | 위험 | 대응 |
|---|---|---|
| R1 | **`delete_folder()`가 하위 프로젝트를 재귀 삭제한다.** 원본은 권한 개념이 0이라 남의 자료·승인본까지 지운다 | 소유자 검사 + "결재 이력 있는 자료가 있으면 거부" 가드 필수 |
| R2 | **결재 코멘트 앵커가 끊길 수 있다.** `ApprovalComments.page_id`는 스냅샷 페이지 id인데 `applyProject()`가 `reseedUids(st.pages)`로 id를 다시 뿌린다 | P5 착수 전 `reseedUids` 동작 확인. 끊기면 스냅샷 id를 안정 키로 별도 보존 |
| R3 | **결재가 1인 병목이다** (D11). 관리자가 자리를 비우면 모든 제출·수정 요청이 멈춘다. 「마지막 관리자 비활성화 불가」 계약(`auth.count_active_admins`)이 최소한의 안전장치이지만 부재 자체는 못 막는다 | 대기 건수를 사이드바 배지로 상시 노출. 장기적으로 대리 결재자를 둘지는 이번 범위 밖 |
| R4 | **기존 계약 테스트 일부 파기.** `test_visibility.py`의 동료 열람 5개(회차 기반)와 `test_열람자는_발행본만_읽는다` | 지우지 말고 **팀 기준으로 다시 쓴다.** 테스트를 지우면 규칙이 사라진다 |
| R5 | `test_endpoint_coverage.py`가 신규 라우트에 가드 누락을 강제 검사한다 | 위험이 아니라 안전망. 그대로 둔다 |
| R6 | **e2e 재작성 물량.** `approval_flow.mjs`는 로그인 없는 상태 전제(`.sh-side .sh-nav` 3개 단언 포함) | `login_password_smoke.mjs`의 로그인 헬퍼를 붙이고 역할별(L1/L2/L3) 시나리오로 재구성 |
| R7 | **"회차"가 두 뜻으로 남는다** — `Approvals.round`(재제출 차수) vs 폐기되는 `Cycles`(월 회차) | UI 문구를 「제출 N차」로 통일. 코드 식별자 `round`는 유지 |
| R8 | 프런트 두 축 충돌 — `useNav.menu` × `useProjects.view`. `LibView`의 `'cycles'` 제거 필요 | P2에서 `LibView`를 `'library' \| 'editor'`로 축소한 뒤 P5에서 셸을 얹는다 |
| R10 | **`key={uid}` 는 전역 스토어를 리셋하지 못한다.** `App.tsx` 주석은 "그러지 않으면 이전 사용자의 이북 목록이 화면에 남는다"고 적어 두었지만, 막으려던 그 일이 실제로 일어나고 있다. 목록만이 아니라 `view`·`activeId`·`useBuilder`(문서 본문)까지 남아, 편집 화면에서 로그아웃하면 다음 사람이 앞사람 슬라이드에 착지한다 | P1.5 에서 로그아웃·계정 변경 시 명시적으로 비운다. 재현 테스트를 함께 넣는다 — 지금 이 경로를 확인하는 테스트가 하나도 없다 |
| R9 | **팀 없는 L2가 제출하면 갈 곳이 없다** (`Approvals.team_id NOT NULL`) | 제출 시 팀 미소속이면 거부 + "관리자에게 팀 배정을 요청하세요" 안내 |
