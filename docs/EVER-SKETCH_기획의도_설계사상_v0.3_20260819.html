1. 기획의도 Why & Background

문제 인식 — 지금 무엇이 불편한가

월 1회 임원회의 자료는 내용이 어려워서 힘든 게 아니다. 내용을 만드는 시간보다 파일을 돌리는 시간이 더 길다.

PPT 작성→ 메일·메신저 발송→ 검사·코멘트(구두/메일)→ 수정→ 재발송→ 버전 혼선→ 취합·양식 정리
  • 왕복 비용 — 작성 → 발송 → 검사 → 수정 → 재발송이 회차마다 반복된다. 실제 소요의 대부분이 이 왕복이다.
  • 버전 분열 — 최종.pptx, 최종_수정.pptx, 최종_진짜최종.pptx. 어느 것이 원본인지 사람이 기억으로 관리한다.
  • 피드백 유실 — 코멘트가 문서 밖(메일·구두·메신저)에 있어 어느 장, 어느 칸 이야기인지 다시 물어야 한다. 반영 여부도 추적되지 않는다.
  • 양식 이탈 — 임원별로 표 모양·글꼴·색이 달라져 취합 단계에서 관리자가 손으로 다시 맞춘다.
  • 열람 통제 부재 — 파일이 나가는 순간 누가 보고 누가 고칠 수 있는지 통제할 방법이 없다.

해결 목표

AS-IS

  • 파일이 이동한다 (첨부·다운로드)
  • 피드백은 문서 밖에 있다
  • 원본은 사람의 기억 속에 있다
  • 양식은 권고사항이다
  • 취합은 관리자의 수작업이다

TO-BE

  • 사람이 링크로 모인다 (원본 1개)
  • 피드백은 그 페이지·그 칸에 붙는다
  • 원본은 서버가 보증한다 (버전 자동기록)
  • 양식은 시스템이 고정한다
  • 취합은 발행 버튼 한 번이다

정량 목표(10월 실전 1회차 실측): 자료 준비 리드타임 50% 단축, 재발송 0회, 취합·양식정리 수작업 80% 감소. 9월 리허설에서 기준선을 잡는다.

존재 이유 — 왜 지금, 왜 우리가

  • 재료가 이미 있다. 편집기(ebook_html), 이북·덱 생성기(uniever_ebook), 개발표준(default_skill)이 각각 동작한다. 새로 만드는 게 아니라 이어 붙여 제품으로 만드는 단계다.
  • 범용 협업툴로는 안 된다. 상용 도구는 고정 표준 양식 + 임원 1인 1장 + 회차 취합 + 이북/PPT 산출이라는 이 회의체 고유의 흐름을 담지 못한다.
  • 사내 파일럿이 곧 레퍼런스다. 유니에버 임원회의에서 검증한 흐름은 그대로 사내 표준 → 상품(솔루션 사업)으로 확장된다. 최종 목적지는 사내 도구가 아니라 비즈니스 모델이다.

2. 설계사상 Philosophy & Principle

핵심 철학 — 다섯 개의 문장

원칙의미와 결과
① 원본은 하나다
Single Source of Truth		 문서는 이동하지 않는다. 사람이 링크로 온다. 파일 첨부는 최종 발행 단계에서만 발생한다. 버전은 서버가 자동 기록한다.
② 권한은 화면이 아니라 데이터에 붙는다 버튼을 숨기는 것은 UX이고, 막는 것은 API다. 모든 읽기·쓰기·삭제는 서버에서 소유자·역할을 검증한다. 프런트 가드는 보조 수단일 뿐이다.
③ 피드백은 문서 안에서 닫힌다 메모는 반드시 페이지(또는 셀)에 앵커된다. 남기기 → 보기 → 고치기 → 해결까지 한 화면에서 끝난다. 문서 밖으로 나가는 코멘트는 만들지 않는다.
④ 자유도는 의도적으로 제한한다 표준 양식은 시스템이 박아둔다. 사용자는 칸 내용, 셀 병합·추가, 글자 크기·굵기 수준까지만 만진다. 자유도를 줄여야 취합이 자동화된다.
⑤ 되돌릴 수 있어야 손이 빨라진다 자동 저장 + 버전 스냅샷 + 복원이 기본. 실수를 되돌릴 수 있다는 확신이 있어야 사용자가 과감히 고친다.

우선순위 — 가치가 충돌할 때

정확성(원본 무결) > 권한·보안 > 취합 자동화 > 편집 자유도 > 화면의 화려함

  • "임원이 원하는 대로 다 편집되게" vs "취합이 자동으로" → 취합 자동화가 이긴다. 편집 자유는 관리자 승인 후 템플릿 자체를 고쳐서 흡수한다.
  • "빨리 쓰게 승인 없이" vs "누가 무엇을 봤는가" → 권한이 이긴다. (그래서 가입은 자유롭게, 권한은 승인제로 나눈다.)
  • "신규 기능 추가" vs "기존 산출 경로 유지" → 기존 산출 경로가 이긴다.

기술 · 구조 원칙

  • 스택 계승 — React + TypeScript + Vite / FastAPI + SQLite. ebook_html을 통째로 복사해 EVER-SKETCH의 출발점으로 삼는다. 폴더 구조를 재편하지 않는다(경로 파손 리스크 회피, 승인된 이탈 문서 그대로 승계).
  • 무수정 계약 유지 — uniever_ebook의 generator.py·덱 빌더는 수정하지 않는다. 연결은 기존 계약(PNG 폴더 산출 → CLI 호출) 그대로. 통합의 방향은 "합치기"가 아니라 "호출하기"다.
  • 단일 상태 모델 — 페이지 = 카드 + 자유 캔버스 요소, 이북 1장 = PNG 1장. 편집·발표·이북·PPTX가 하나의 상태에서 나온다.
  • 표준스킬 준수 — default_skill의 G0~G6 게이트·UI 표준·검증 증적을 개발 프로세스에 적용. 화면 작업은 uniever-development-standard 필수 경유.
  • 확장 여지만 열어둔다 — SSO/AD, PostgreSQL, 멀티테넌시는 인터페이스만 분리하고 구현은 미룬다. 지금 만들지 않는다.

4. 핵심 기능 ① — 가입 · 승인 · 권한 3역할

가입 흐름 (확정)

사내 사용자 자가가입→ 희망 역할 본인 선택
(열람자 / 작성자 / 관리자)→ 승인 대기 상태
= 아무것도 못 봄→ Lv1 관리자 승인·역할 확정→ 실권한 부여
왜 승인 단계가 반드시 필요한가. 가입 즉시 본인이 고른 역할이 그대로 적용되면, 링크를 아는 누구나 관리자를 골라 임원 자료 전체를 열람하고 삭제할 수 있다. 그래서 "본인이 고른다"는 사용자 경험은 그대로 두되, 그것을 신청(희망 역할)으로 처리하고 실권한은 관리자 승인 시점에 부여한다. 승인 전 계정은 로그인은 되지만 "승인 대기" 화면만 보이고, 어떤 이북에도 접근하지 못한다. 관리자 승인은 기존 관리자만 가능하며, 최초 관리자 1명은 시드 계정으로 생성한다.

권한 매트릭스

권한대상권한보이는 범위
Lv1 관리자회의 주관·기획 담당 작성 · 수정 · 삭제 + 가입 승인·권한 변경·비활성화 + 회차 개설/마감 + 템플릿 배부 + 전체 이북 열람 + 메모 작성·해결 + 최종 발행 전체
Lv2 작성자임원 · 부서 담당자 작성 · 수정(본인 이북) + 본인 이북의 메모 확인·답글·해결요청. 삭제 불가, 타인 이북 접근 불가 본인 이북 + 발행본
Lv3 열람자일반 참석자·공유 대상 읽기 전용. 편집·삭제 불가, 메모 작성·열람 모두 불가 발행된 회차 결과물
  • 소유 기반 — 모든 이북에 owner_id. 작성자는 "내 것"만, 관리자는 "전부". 판정은 서버 미들웨어 한 곳에서 한다.
  • 삭제는 관리자만 — 작성자의 삭제 요청은 "삭제 요청" 상태로 남기고 실제 삭제는 관리자가 승인(회차 자료 유실 방지). v1.1로 이월
  • 회귀 테스트 고정 — 모든 엔드포인트에 관리자·작성자·열람자 + 승인대기 4개 계정 자동 테스트를 스위트로 박는다.

5. 핵심 기능 ② — 메모 피드백 루프

항목정의
앵커이북 > 페이지 > (선택)요소·셀 좌표. 클릭하면 해당 위치로 스크롤·하이라이트
상태열림 → 수정함 → 해결 (해결 권한은 메모 작성자 또는 관리자)
노출 범위관리자 전원 + 해당 이북의 작성자 소유자에게만. Lv3 열람자에게는 메모 존재 자체를 노출하지 않는다 (확정)
