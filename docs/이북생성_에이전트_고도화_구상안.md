# 이북 생성 에이전트 고도화 구상안

> ebook_html 챗 에이전트를 **명령 라우터 → 생성·대화형 플래너**로 승격한다.
> 목표: **"브리프 한 줄 → 완성 이북"을 한 번에 자동 생성하고, 마음에 안 들면 대화로 계속 고친다.**

## 1. 현재 구조 진단

- `server/intent/` = **한 문장 = 한 액션** 명령 라우터 (HELIX 분류기 이식).
  - 3단 분류: 고신호 정규식 → 키워드 점수 → 애매하면 gemma 판별. A/B/C/X 확신 등급 + 되묻기.
- LLM(gemma) 역할은 두 개뿐: **(1) 의도 애매할 때 후보 판별, (2) 자유 대화.** → **이북 "내용"은 LLM이 안 쓴다.**
- 콘텐츠 생성 씨앗 1개 존재: `summarizeNotes()` → `/api/summarize` (가져온 HTML 본문을 헤드라인+불릿 카드로 요약).
- 카드 콘텐츠 모델은 깔끔: `Page{cardKey, fields{}}` + `registry.ts`가 카드별 필드 정의.
  → **gemma가 `[{cardKey, fields}]` JSON만 내면 그대로 카드로 꽂힌다. 생성 에이전트 재료가 이미 다 있음.**

## 2. 목표 아키텍처 — 3레인 오케스트레이터

맨 앞에 얇은 **레인 분류기**를 얹어 세 갈래로 라우팅한다.

```
사용자 입력 + BookState 스냅샷
        │
   [레인 분류기]  create_book | edit_content | command | chat
        │
 ┌──────┼───────────────┬──────────────────┐
 │ command              │ create_book       │ edit_content
 │ (기존 intent 엔진)   │ (신규 플래너)     │ (신규 부분수정)
 │ 다크로/도형 넣어     │ 브리프→BookPlan   │ 이 장 다듬어/3장 추가
 │ → 결정론적 UI 액션   │ → apply_book_plan │ → apply_page_edits
 └──────────────────────┴───────────────────┴──────────────────┘
        │
   [품질 하네스] 파싱·스키마검증·재시도·수치가드·폴백
        │
   ui_action → 프론트 applyUiAction → store
```

- **command 레인**: 기존 `intent/` 그대로 유지(빠르고 결정론적).
- **create_book 레인**: gemma가 이북 설계 JSON 생성 → 전체 카드 적용(즉시).
- **edit_content 레인**: 현재 문서 컨텍스트 기준으로 **대상 페이지만** 수정.

## 3. 핵심 조각 5개

### 3-1. 문서 상태 계약 (②의 기반)
프론트가 **매 턴** 현재 이북 스냅샷을 서버로 전송 → 서버가 세션에 보관.
이게 깔려야 "이 장", "빠진 섹션", "톤 통일"이 가능. 프론트가 매 턴 최신값을 보내므로 **단일 진실원**.

```jsonc
// BookState (요청에 동봉)
{
  "title": "유니에버 AX 사업모델",
  "orientation": "portrait",
  "theme": "light",
  "selectedPageId": 12,
  "pages": [
    { "id": 11, "cardKey": "cover", "title": "유니에버 AI팩토리", "summary": "부제: 2026 경영보고" },
    { "id": 12, "cardKey": "kpi",   "title": "기대 성과", "summary": "불량률:-30% / 검사시간:-40% / ROI:14개월" }
    // ... 페이지별 1줄 요약(길면 절삭)
  ]
}
```
- 수정 레인이 특정 페이지 전체 필드를 알아야 할 땐 `selectedPageId` 페이지의 full `fields`를 함께 첨부(또는 id로 재조회).

### 3-2. 이북 설계 스키마 (①의 계약)
플래너 LLM 출력 = 책 레벨 메타 + 순서 있는 페이지 스펙 배열. 각 페이지는 `registry`의 cardKey/필드에 맞춘다.

```jsonc
// BookPlan (플래너 출력)
{
  "title": "유니에버 AI팩토리 소개",
  "orientation": "portrait",
  "theme": "dark",
  "pages": [
    { "cardKey": "cover",   "fields": { "title": "유니에버 AI팩토리", "sub": "현장 데이터로 품질을 바꾸다" } },
    { "cardKey": "toc",     "fields": {} },
    { "cardKey": "summary", "fields": { "title": "핵심 요약", "body": "…" } },
    { "cardKey": "market",  "fields": { "title": "시장과 경쟁", "p1": "…", "p2": "…" } },
    { "cardKey": "kpi",     "fields": { "title": "기대 성과", "k1": "불량률:-30%", "k2": "…", "k3": "…" } },
    { "cardKey": "roadmap", "fields": { "title": "로드맵", "p1": "PoC : 1분기", "p2": "확산 : 3분기" } },
    { "cardKey": "closing", "fields": { "title": "함께 시작합시다", "sub": "" } }
  ]
}
```
- **핵심 신규 재료: 서버측 카드 카탈로그 미러.** `registry.ts`(cardKey·필드·예시)를 서버 스펙으로 복제해 플래너 프롬프트에 "쓸 수 있는 카드와 필드"로 주입. → gemma가 규격 안에서만 JSON 생성.
- 카탈로그는 **한 곳(정본)**에서 관리하고 프론트/서버가 공유하도록(드리프트 방지).

### 3-3. 배치 적용 브리지
`src/chat/actions.ts` 액션 2종 추가 + `src/state/store.ts` 액션 추가.

| 액션 | 페이로드 | 동작 |
|---|---|---|
| `apply_book_plan` | `BookPlan` | `store.applyPlan()` — 페이지 전체 세팅. cover/toc/kind 처리, title·theme·orientation 반영 |
| `apply_page_edits` | `[{pageId, fields}]` | 페이지별 `setCard`/`updateField` — 대상만 수정 |

- 기존 `addCard`/`setCard`/`defaultsFor`를 재활용 → 매핑만 신규.
- 즉시 적용(결정 사항). **되돌리기(undo)** 로 안전망 확보.

### 3-4. 품질 하네스 (⑤ — 완전자동엔 필수)
gemma3:27b로 "책 한 권 JSON"은 가끔 깨지므로 플래너를 감싼다.

1. **파싱 + 스키마 검증**: 모르는 cardKey 드롭, 누락 필드는 registry 예시/기본값으로 보정.
2. **재시도**: 파싱 실패 시 1~2회 재요청("JSON만" 강조, 실패 원문 힌트).
3. **수치 환각 가드**: 사용자가 안 준 KPI/숫자를 지어내지 않음 → 없으면 `예시)` 프리픽스 또는 빈칸 + 되묻기.
4. **폴백**: 최악의 경우 표지/목차/요약/마무리 최소 골격이라도 생성.
5. (선택) **자기검증 패스**: 생성 후 빈 필드·과장문구·중복목차 점검 → 수정. dev-standard의 하네스/루프·verification-before-completion과 연동.

### 3-5. 대화형 루프
- 세션 히스토리는 이미 `_SESSIONS`에 존재 → 직전 BookPlan/스냅샷을 세션에 얹어 "3장 더", "아까 톤 유지" 연결.
- 수정은 항상 프론트가 보내는 **최신 BookState 기준 diff**.

### 3-6. 스타일: 시각 테마(EVER-PEAK 고정) × 콘텐츠 톤(브리프별 유연)
"스타일"을 **서로 독립된 2개 층**으로 분리하면, "EVER-PEAK 스타일 고정"과 "브리프마다 유연"이 충돌하지 않는다.

| 층 | 무엇 | 누가 결정 | 유연성 |
|---|---|---|---|
| **시각 테마(렌더링)** | 색·타이포·KPI칩·다크/라이트·표지 배경 | 테마 토큰 (고정, 재사용) | 테마 몇 종 중 선택 |
| **콘텐츠·톤(문안)** | 헤드라인 문구·불릿 밀도·섹션 구성·어투 | 플래너 LLM | **브리프마다 유연** |

- **EVER-PEAK에서 고도화가 쉬운 이유**: EVER-PEAK 라이트/다크가 **이미 `src/design/tokens.ts`의 `themes`에 토큰으로 이식돼 있음**
  (라이트=EVER-PEAK 솔루션소개, 다크=EVER-PEAK 다크: `page/ink/body/blue/kick/card/coverBg…`).
  `build_everpeak_deck.py`(uniever_ebook 계열, 무수정 대상)를 포팅할 필요 없이, **이미 있는 테마를 확장·정교화**(카드별 스타일 매칭)만 하면 된다.
  참고: `docs/이북개선계획_EVERPEAK다크_목차이동_v1.0.html`에 EVER-PEAK 다크 개선이 이미 진행 중.
- **플래너는 시각을 만들지 않는다**: BookPlan의 `theme`만 고르고(예: `dark`), 콘텐츠는 브리프대로. 렌더는 테마가 EVER-PEAK 룩으로 처리.
- **결론**: 시각은 EVER-PEAK 테마로 안정적으로 예쁘게, 문안·구성은 매번 다르게 → **둘 다 동시에 성립.**

## 4. 빌드 순서 (각 단계 독립 실행 가능)

| 게이트 | 내용 | 산출물 | 수용 기준 |
|---|---|---|---|
| **G1** | 문서 컨텍스트 계약 | 프론트 BookState 전송 + 서버 수신·세션 보관 | 서버 로그에 매 턴 현재 페이지 목록이 찍힘 |
| **G2** | 서버측 카드 카탈로그 미러 | registry → 서버 카드 스펙(정본 공유) | 플래너 프롬프트에 13종 카드·필드가 주입됨 |
| **G3** | BookPlan 생성 + 검증 하네스 | 브리프 → 검증된 BookPlan JSON | 깨진 JSON도 재시도/보정 후 유효 플랜 반환 |
| **G4** | apply_book_plan 브리지 | `store.applyPlan()` + 액션 | "…이북 만들어줘" → 카드 통째로 생성됨 |
| **G5** | 부분 수정 루프 | edit_content 레인 + apply_page_edits | "이 장 다듬어/3장 추가/톤 통일" 동작 |
| **G6** | 자동 export + 자기검증 | "만들어줘" 끝에 이북까지 + 검증 패스 | 브리프 한 줄 → PNG 폴더 → generator.py → 이북 |

- **G1~G4 = "말로 초안 뽑기"**, **G5~G6 = "대화로 완성 + 완전자동"**.

## 5. 열린 이슈 / 다음에 정할 것

- 서버 카드 카탈로그를 **어디를 정본으로** 둘지(TS→JSON export vs 서버 수기 미러) — 드리프트 방지책 필요.
- 페이지 수/구성 기본값: 브리프에 장수 명시 없을 때 기본 몇 장·어떤 골격?
- `viz` 카드(flow/mindmap/board 등) 생성 범위: 1차는 텍스트형 카드 위주, 다이어그램 카드는 2차?
- gemma 품질 실측 후 상위모델 교체 지점(플래너만 provider 분리 옵션).
- 자동 export를 "만들어줘"에 항상 붙일지, "이북으로 뽑아줘"에서만 트리거할지.
- EVER-PEAK 테마 정교화 범위: 카드별(cover/kpi/roadmap…) 스타일을 EVER-PEAK 룩에 어디까지 맞출지 — `docs/이북개선계획_EVERPEAK다크_목차이동_v1.0.html` 작업과 합류 지점 정리.

## 6. 불변 계약 (재확인)
- `uniever_ebook`은 수정하지 않는다. 연결은 PNG 폴더 산출 → `generator.py` CLI.
- 각 페이지 = 이북 한 장(PNG). 카드 + 자유 캔버스 요소는 한 장에 합쳐 렌더.
- 화면(카드/캔버스) 작업은 uniever-development-standard 준수, 완료 전 verification-before-completion.
