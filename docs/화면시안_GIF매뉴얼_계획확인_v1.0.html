확인제가 이해한 것

✓12장 구성은 그대로
뼈대는 살리고, 예시 그림 자리를 실제 GIF 로 바꿉니다.
✓정지 슬라이드가 아니라 GIF
「이렇게 생겼습니다」가 아니라 「이렇게 누르면 이렇게 됩니다」를 보여 줍니다.
✗구성안 HTML 은 공유물이 아님
제가 만든 시안들은 작업용입니다. 남에게 나가는 건 매뉴얼뿐입니다.
✗Lv1·Lv3 편은 안 만듦
지금 단계는 Lv2 작성자 매뉴얼 하나입니다.
✓트리·머메이드가 먼저
기능을 만든 다음에 GIF 를 찍습니다.
✓이유도 이해했습니다
안 만들고 찍으면 곧 갈아엎을 화면을 찍게 됩니다. 12편을 다시 찍는 건 다시 그리는 것보다 비쌉니다.
덤으로 얻는 게 있습니다. 트리·머메이드를 만들면 4·6·7·8 장의 그림이 그 도구로 만들어지는 장면 자체가 되어, 설명과 예시가 한 편의 GIF 로 합쳐집니다. 순서를 그렇게 잡으신 게 맞습니다.

계측GIF 가 지금 EVER-SKETCH 에서 실제로 어떻게 되나

찍기 전에 재 봐야 할 것이라 먼저 확인했습니다. 반은 되고 반은 안 됩니다.

확인한 것결과
편집기·뷰어에서 GIF 가 움직이나○ `<img>` 로 그리므로 그대로 움직입니다
긴 변 1600px 이하면 원본 그대로 들어가나○ 애니메이션 유지
긴 변 1600px 초과면✗ 캔버스로 다시 그려서 첫 프레임만 남습니다 — 아무 말도 없이
이미지를 어디에 저장하나문서 안에 base64 로 통째로. 파일 업로드 엔드포인트가 없습니다
저장할 때 무엇을 보내나문서 전체를 매번 PUT 합니다
PPTX 로 내보내면그림은 들어가지만 정지합니다
문서 크기 제한서버에 없습니다 — 막아 주는 게 없다는 뜻이기도 합니다

그래서 크기가 문제입니다

녹화GIF문서 안에서(base64)12편이면
10초 · 1200×800 · 10fps3.5MB4.8MB57MB
10초 · 1600×1000 · 12fps6.0MB8.2MB98MB
6초 · 900×600 · 8fps1.2MB1.6MB20MB
도구가 스스로 남긴 경고가 이미 있습니다. imageIntake.ts 첫머리에 이렇게 적혀 있습니다 — 「3MB 사진 5장이면 base64 로 약 20MB 이고, 도형을 한 번 움직일 때마다 그 20MB 를 딥카피 + stringify 해서 통째로 올린다 — 클릭 한 번마다 화면이 수백 ms 멎는다. 근본 해결은 서버에 blob 업로드 엔드포인트를 두고 URL 만 저장하는 것이다.」 GIF 매뉴얼은 정확히 그 상황을 12배로 만드는 일입니다.

고르기GIF 를 어디에 담을까요 — 셋 중 하나

안무엇을 하나드는 값결과
ㄱ · 파일 업로드를 만든다 서버에 이미지 저장 엔드포인트를 두고 문서에는 URL 만 저장 중간 — 업로드 라우트 + 저장 자리 + 권한 근본 해결. 매뉴얼도 사진 많은 자료도 전부 가벼워집니다
ㄴ · 매뉴얼만 밖에 둔다 GIF 붙인 HTML 한 장을 따로 두고, 이북에는 정지컷 + 「영상 보기」 거의 없음 빠르지만 매뉴얼이 EVER-SKETCH 밖에 있게 됩니다
ㄷ · GIF 를 작게 유지 900×600 · 6초 · 8fps 로 못박고 이북 안에 넣음 없음 12편 20MB. 편집할 때마다 그게 통째로 올라갑니다
제 의견은 ㄱ 입니다. 트리·머메이드를 만들고 나면 그다음 할 일이 GIF 인데, 어차피 한 번은 부딪힐 벽입니다. 그리고 이건 매뉴얼만의 문제가 아닙니다 — 임원들이 실물 PPT 를 변환해 쓰는 자료가 이미 사진 덩어리입니다. 다만 ㄱ 을 지금 하면 트리·머메이드가 그만큼 밀립니다.
급하시면 ㄴ 으로 먼저 내고, ㄱ 을 한 뒤에 매뉴얼을 안으로 들여오는 길도 있습니다.
어느 쪽을 고르셔도 지금 바로 막아야 할 것이 하나 있습니다. 1600px 넘는 GIF 가 아무 말 없이 정지 이미지가 되는 것 — 찍어서 넣고 나중에야 「왜 안 움직이지」를 알게 됩니다. 「움직이는 그림은 줄이지 않습니다. 1600px 이하로 녹화해 주세요」 한 줄만 있으면 됩니다. 작은 일입니다.

촬영GIF 12편 — 무엇을 찍나

길이는 6~10초, 한 편에 한 가지만. 길면 안 봅니다. 초록 표는 트리·머메이드가 있어야 찍을 수 있는 편입니다.
