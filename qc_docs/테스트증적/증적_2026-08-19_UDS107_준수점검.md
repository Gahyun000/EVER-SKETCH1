## 2. 이번에 발견해 고친 것

### 2.1 입력 길이 상한이 없었다 (§6)

`signup`에 아이디 최소 3자, 비밀번호 최소 8자만 있고 **상한이 하나도 없었다.**

| 항목 | 조치 |
|---|---|
| 비밀번호 | 128자 상한. **없으면 연산 DoS가 된다** — PBKDF2는 입력 길이에 비례해 CPU를 쓰므로, 10MB짜리 비밀번호를 반복 전송하면 로그인 요청 하나가 서버 코어를 통째로 점유한다. `login()`은 해시 계산 **전에** 길이를 먼저 자른다 |
| 아이디 | 3~32자 + `^[a-z0-9._-]+$`. 공백·제어문자·따옴표가 섞인 아이디는 화면과 감사로그를 오염시킨다 |
| 이름·부서 | 각 40자 |

### 2.2 삭제·발행이 감사로그에 없었다 (§4)

로그인·승인·레벨변경·비활성화만 기록하고 있었다. 표준이 명시한 "삭제, 배포"가 빠져 있었다.

- `delete_project` — 이름·소유자를 함께 기록(삭제 후에는 조회 불가)
- `delete_version`
- `publish` — `/api/build` 성공 시

### 2.3 로그인 시도 제한이 없었다 (§6)

10분 내 10회 실패 시 잠금. 별도 테이블 없이 `AuditLogs`의 `login_fail`을 카운터로 쓴다.

- 잠금은 **계정별**로 분리 — 한 사람이 잠겼다고 다른 사람이 막히면 안 된다
- 로그인 성공 시 실패 기록을 잠금 계산에서 제외(이력 자체는 보존)
- 임원이 잠긴 경우의 탈출구: `admin_cli unlock --login <아이디>`

### 2.4 중요 작업에 확인 단계가 없었다 (§4)

사용자 관리 화면에서 **클릭 한 번**으로 관리자 부여와 계정 중지가 실행됐다. 확인 다이얼로그를 넣고, 그 작업이 실제로 무엇을 뜻하는지(모든 임원 자료 열람 가능 / 즉시 로그아웃) 문장으로 적었다.

## 5. 2차 조치 (2026-08-19) — 미배선 엔드포인트 전건 처리

1차 점검에서 "W2 착수 첫 작업"으로 이월했던 항목을 즉시 처리했다.

### 5.1 처리 결과

**전 엔드포인트 33개 중 무인증은 `/api/health` 하나뿐이다.** 그 하나도 내부 경로 노출을 제거했다.

| 엔드포인트 | 이전 | 이후 | 근거 |
|---|---|---|---|
| `GET/PUT /api/settings/llm` | **무인증** | 관리자 (`SETTINGS_MANAGE`) | §5 비밀정보 — API 키 |
| `POST /api/settings/llm/test` | **무인증** | 관리자 (`SETTINGS_MANAGE`) | §6 SSRF |
| `POST /api/build` | **무인증** | 관리자 (`PUBLISH`) | 발행 = 열람자 전원 공개 |
| `POST /api/deck`, `/api/deck/stream` | **무인증** | 작성자 이상 (`AI_USE`) | 작성 도구 |
| `POST /api/chat/v2`, `/v2/stream`, `/reset` | **무인증** | 작성자 이상 (`AI_USE`) + 대화 소유 확정 | §3 AI 사용 제한 |
| `GET/DELETE /api/chat/conversations*` | **무인증** | 작성자 이상 + 소유자 대조 | 아래 5.3 |
| `POST /api/export/docx` | **무인증** | 작성자 이상 (`AI_USE`) | 작성 도구 |
| `POST /api/summarize`, `/plan`, `/edit` | **무인증** | 작성자 이상 (`AI_USE`) | §3 AI 사용 제한 |
| `GET /api/health` | 무인증 + **절대경로 노출** | 무인증, 존재 여부만 | §6 내부 경로 미노출 |

### 5.2 이번에 드러난 것 — SSRF

`POST /api/settings/llm/test`는 **요청 본문의 `base_url`로 서버가 직접 HTTP 요청을 보낸다.**
무인증 상태였으므로, 사내망에 닿을 수 있는 누구나 이 서버를 경유해 임의 주소로 요청을 만들 수 있었다.
UDS-107 §6이 SSRF를 위협 모델에 명시적으로 포함한다. 관리자 전용으로 제한했다.

`PUT /api/settings/llm`은 읽기보다 위험했다 — `base_url`을 공격자 서버로 바꾸면
**이후 모든 챗봇 대화가 그쪽으로 전송된다.** 읽기(GET)는 키를 마스킹해 내보내고 있었지만
쓰기는 아무 제한이 없었다.

### 5.3 챗봇 대화가 사용자별로 분리되어 있지 않았다

`Conversations` 테이블에 소유자 컬럼이 없었다. 단일 사용자 도구였을 때는 맞는 설계지만,
다중 사용자가 되는 순간 **임원 A가 대화 목록에서 임원 B의 챗봇 대화를 그대로 읽는다.**
임원회의 자료를 다루는 대화이므로 내용 자체가 §2 기준 "내부" 이상이다.

- `Conversations.user_id` 추가 (기존 DB에도 안전하게)
- 목록은 본인 것만. 관리자는 전체(이관·감사 목적)
- 개별 조회·삭제는 소유자 대조
- 주인 없는 기존 대화는 최초 접근자에게 1회 귀속(`claim`), 이미 주인이 있으면 불변

### 5.4 재발 방지 — 배선 누락 자체를 테스트로 고정

`server/test_endpoint_coverage.py`를 추가했다. `app.py`·`routes_projects.py`·`routes_auth.py`를
**AST로 파싱해 모든 라우트를 열거하고**, 각각에 로그인 가드와 권한 판정이 있는지 검사한다.

- 새 엔드포인트를 추가하고 가드를 빼먹으면 **테스트가 실패한다**
- 공개 허용목록은 1건으로 고정 — 늘리려면 테스트를 함께 고쳐야 하므로 의식적 결정이 된다
- 라우트 파싱이 0건이 되면(리팩터링으로 구조가 바뀌는 경우) 그것도 실패로 잡는다

이 항목이 이번 점검에서 가장 중요하다. **사람이 기억할 일을 스위트가 기억하게 만들었다** —
1차 점검에서 갭이 나온 이유 자체가 "W1 범위 밖이라 안 봤다"였기 때문이다.

### 5.5 2차 게이트 판정

| 항목 | 결과 |
|---|---|
| 전 엔드포인트 인증 배선 | **통과** — 33개 중 공개 1개(`/api/health`), 사유 기록 |
| §5 비밀정보 (LLM 키) | **통과** — 읽기·쓰기·테스트 모두 관리자 |
| §6 SSRF | **통과** — 관리자 제한 |
