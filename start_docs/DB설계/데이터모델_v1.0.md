## 1. 기존 테이블 (승계)

`ebook_html`에서 그대로 넘어온 테이블. 스키마는 `server/projects.py`, `server/notes.py`, `server/settings_store.py`, `server/conversations.py`가 `CREATE TABLE IF NOT EXISTS`로 자체 생성한다.

| 테이블 | 역할 | 변경 |
|---|---|---|
| `Projects` | 이북(작업본). `state` 컬럼에 편집 상태 JSON 전체 | **확장** |
| `ProjectVersions` | 버전 스냅샷 (자동/이름/고정, 보존 정책 포함) | 그대로 |
| `Notes` | 프로젝트별 메모장 (블록 배열) | `Comments`로 **승계·확장** |
| `App_Settings` | LLM 설정 | 그대로 |
| `Conversations` | 채팅 이력 | 그대로 |

> **주의** — 시간 컬럼 단위가 섞여 있다. `Projects`/`ProjectVersions`는 **밀리초**(JS `Date` 호환, `_now() = int(time.time()*1000)`), `Notes`는 **초**(`time.time()`). 신규 테이블은 **밀리초로 통일**하고, `Notes` → `Comments` 이관 시 ×1000 변환한다.

## 2. 신규 테이블

### 2.1 `Users`

```sql
CREATE TABLE IF NOT EXISTS Users(
  id               TEXT PRIMARY KEY,       -- 'u' + uuid12
  login_id         TEXT NOT NULL UNIQUE,   -- 사내 로그인 ID
  pw_hash          TEXT NOT NULL,          -- PBKDF2-HMAC-SHA256 (salt 포함)
  name             TEXT NOT NULL,
  dept             TEXT,
  requested_level  INTEGER NOT NULL,       -- 1|2|3 가입 시 본인이 고른 희망 레벨
  level            INTEGER NOT NULL DEFAULT 0,  -- 0=미부여, 1|2|3 = 실권한
  status           TEXT NOT NULL DEFAULT 'pending',  -- pending|active|disabled
  created_at       REAL NOT NULL,          -- ms
  approved_at      REAL,
  approved_by      TEXT,                   -- Users.id (L3)
  last_login_at    REAL
);
CREATE INDEX IF NOT EXISTS idx_users_status ON Users(status);
```

**핵심: `requested_level`과 `level`은 다른 컬럼이다.** 가입 시점에는 `requested_level`만 채우고 `level = 0`, `status = 'pending'`. L3가 승인할 때 비로소 `level`이 채워진다.

이 분리가 없으면 링크를 아는 누구나 L3를 골라 임원 자료 전체를 열람·삭제할 수 있다.

| 상태 | 로그인 | 볼 수 있는 것 |
|---|---|---|
| `pending` | 가능 | "승인 대기" 화면만. 어떤 이북에도 접근 불가 |
| `active` | 가능 | `level`에 따라 |
| `disabled` | **불가** | 없음 |

- 비밀번호는 평문 저장 금지. `hashlib.pbkdf2_hmac('sha256', pw, salt, 200_000)`, 저장 형식 `pbkdf2$200000$<salt_hex>$<hash_hex>`.
- **L3 승인은 기존 L3만 가능.**
- 자기 자신의 레벨은 변경 불가. 마지막 남은 `active` L3는 비활성화 불가(관리자 잠김 방지).

#### 시드 L3 계정 (확정)

| 항목 | 값 |
|---|---|
| `login_id` | **`admin`** |
| `name` | 시스템 관리자 |
| `level` / `status` | 3 / `active` |
| 초기 비밀번호 | 최초 1회 로그인 시 **강제 변경**(변경 전에는 다른 화면 진입 차단) |

운영 방침 — `admin`은 **비상용으로만 남긴다.** 실제 운영 관리자(회의 주관 담당)는 별도 계정을
발급해 L3로 승인하고, 평소 승인·발행은 그 계정으로 한다. 감사로그에서 "누가 한 일"이 구분되어야
하기 때문이다. 공용 계정으로 계속 쓰면 `AuditLogs.user_id`가 전부 `admin`이 되어 로그가 무의미해진다.

### 2.2 `Sessions`

```sql
CREATE TABLE IF NOT EXISTS Sessions(
  token       TEXT PRIMARY KEY,   -- secrets.token_urlsafe(32)
  user_id     TEXT NOT NULL,
  created_at  REAL NOT NULL,      -- ms
  expires_at  REAL NOT NULL,      -- ms
  ip          TEXT,
  user_agent  TEXT
);
CREATE INDEX IF NOT EXISTS idx_sessions_user ON Sessions(user_id);
```

- 쿠키는 `HttpOnly` + `SameSite=Lax`. `Secure`는 **환경변수 `EVER_SKETCH_HTTPS=1`로 켠다**(§2.2.1).
- 유효기간 12시간, 활동 시 갱신.
- 레벨 변경·비활성화 시 **해당 사용자의 세션을 전부 삭제**한다. 그러지 않으면 강등된 사용자가 기존 토큰으로 옛 권한을 계속 쓴다.

#### 2.2.1 배포 형태 — 사내망 + VPN (확정 2026-08-19)

| 항목 | 결정 |
|---|---|
| 서버 위치 | **사내망 사설 IP** (고정). 포트포워딩 **하지 않는다** |
| 외부 접속 | **사내 VPN 경유.** 이미 운영 중인 VPN을 그대로 쓴다 — 추가 개발 0 |
| 프로토콜 | **HTTP.** 인터넷에 노출되지 않고 VPN 구간이 이미 암호화되므로 자체서명 인증서의 브라우저 경고를 감수할 이유가 없다 |
| 쿠키 `Secure` | **끈다** (`EVER_SKETCH_HTTPS` 미설정 시 기본). HTTP에 `Secure`를 붙이면 쿠키가 저장되지 않아 로그인 자체가 안 된다 |
| CORS | **무관.** `server/app.py:693`이 빌드된 `dist/`를 같은 uvicorn의 `/`에 마운트하므로 운영에서는 프런트·API가 동일 오리진이다. `allow_origins=["*"]`는 `npm run dev`(Vite 5173 → API 8000) 전용 |
| 바인딩 | `0.0.0.0` (`run.command`/`run.cmd`의 `HOST` 변수, 기본값). 사내망 전체에서 보이되 공유기가 포워딩하지 않으므로 인터넷 노출 아님 |

**자가가입을 유지할 수 있는 근거가 여기에 있다.** 가입 화면에 도달하려면 사내망 또는 VPN 안에 있어야 하므로
"링크를 아는 누구나"의 범위가 사내 인원으로 한정된다. 인터넷에 직접 노출했다면 자가가입을 닫고
초대 코드·사번 화이트리스트로 바꿔야 했다.

> **전제가 깨지는 조건** — 향후 공인 IP에 포트포워딩하거나 터널을 붙이는 순간 위 근거가 무효가 된다.
> 그때는 ① 자가가입 폐쇄 ② HTTPS ③ 로그인 시도 제한을 **함께** 넣어야 한다. 셋 중 하나만 빠져도 의미가 없다.

### 2.3 `Cycles`

```sql
CREATE TABLE IF NOT EXISTS Cycles(
  id           TEXT PRIMARY KEY,   -- 'c' + uuid12
  title        TEXT NOT NULL,      -- '2026-10 임원회의'
  period_ym    TEXT NOT NULL,      -- '2026-10' (Today 마커·연도 헤더 계산 기준)
  status       TEXT NOT NULL,      -- draft|writing|review|published|closed
  due_at       REAL,               -- ms 제출기한
  template_id  TEXT,               -- Templates.id
  created_by   TEXT NOT NULL,      -- Users.id (L3)
  created_at   REAL NOT NULL,
  published_at REAL,
  closed_at    REAL
);
```

상태 전이: `draft → writing → review → published → closed` (역행은 L3만, `closed`는 종착).

`period_ym`이 있어야 템플릿의 Today 마커와 연도 헤더를 자동 계산할 수 있다(템플릿 사양 §3.4).

### 2.4 `Templates`

```sql
CREATE TABLE IF NOT EXISTS Templates(
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,       -- '월간 임원보고 정본'
  version     TEXT NOT NULL,       -- 'v1.0'
  state       TEXT NOT NULL,       -- Page JSON (슬롯 el 포함)
  slot_policy TEXT NOT NULL,       -- 슬롯별 편집 허용 규칙 JSON
  active      INTEGER DEFAULT 1,
  created_by  TEXT,
  created_at  REAL NOT NULL
);
```

> 기획서 §7 표에는 없던 테이블이다. `Cycles.template_id`가 가리킬 실체가 필요해 추가한다.
> 정본을 파일이 아니라 DB에 두는 이유 — L3가 화면에서 정본을 고칠 수 있어야 하고(설계사상 ④ "초과 요구는 템플릿 자체 개선으로 흡수"), 회차마다 **그 시점의 정본**이 무엇이었는지 남아야 한다.

`slot_policy` 예시:

```json
{
  "head":   {"edit": []},
  "SLOT-A": {"edit": ["cell", "merge", "row", "align", "cbg"], "cbgPalette": ["#2462EB","#EAF1FE","#D98A2A","#EEF0F4"]},
  "SLOT-B": {"edit": ["cell", "row", "format"]},
  "SLOT-C": {"edit": ["cell", "row", "format"]},
  "SLOT-D": {"edit": ["cell", "row", "format"]}
}
```

`col`(열 추가·삭제)이 어느 슬롯에도 없다는 점이 핵심이다.

### 2.5 `Comments` — 기존 `Notes` 승계·확장

```sql
CREATE TABLE IF NOT EXISTS Comments(
  id          TEXT PRIMARY KEY,
  project_id  TEXT NOT NULL,      -- Projects.id
  page_id     INTEGER,            -- Page.id (state JSON 내부)
  anchor      TEXT,               -- JSON: {"elId":123,"r":2,"c":5} 또는 null(페이지 전체)
  author_id   TEXT NOT NULL,      -- Users.id
  body        TEXT NOT NULL,
  status      TEXT NOT NULL DEFAULT 'open',  -- open|fixed|closed
  parent_id   TEXT,               -- 답글이면 부모 Comments.id
  created_at  REAL NOT NULL,      -- ms
  updated_at  REAL,
  resolved_by TEXT,
  resolved_at REAL
);
CREATE INDEX IF NOT EXISTS idx_comments_project ON Comments(project_id);
CREATE INDEX IF NOT EXISTS idx_comments_status  ON Comments(project_id, status);
```

- 상태 전이: `open → fixed → closed`. `closed` 권한은 **메모 작성자 또는 L3**.
- **노출 범위 (확정)** — L3 전원 + 해당 이북의 L2 소유자에게만. **L1에게는 메모 존재 자체를 노출하지 않는다.** 서버가 목록 응답에서 아예 제외한다(프런트에서 숨기는 것이 아니다).
- 삭제해도 이력에 남긴다 → 물리 삭제 대신 `status='deleted'`가 아니라 별도 `deleted_at` 컬럼을 W1.1에 추가. MVP는 물리 삭제 없음.
- 회차 마감 시 `status != 'closed'` 개수를 "미해결 N건"으로 요약.

### 2.6 `AuditLogs` (MVP 축소판)

```sql
CREATE TABLE IF NOT EXISTS AuditLogs(
  id       INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id  TEXT,
  action   TEXT NOT NULL,   -- login|login_fail|approve|level_change|disable|publish|delete
  target   TEXT,            -- 대상 id
  ts       REAL NOT NULL,   -- ms
  detail   TEXT             -- JSON
);
CREATE INDEX IF NOT EXISTS idx_audit_ts ON AuditLogs(ts);
```

MVP는 **로그인 · 승인 · 레벨변경 · 비활성화 · 발행 · 삭제**만 기록한다. 열람 이력 전수는 v1.1로 이월.

## 4. 권한 판정 — 단일 지점

```
GET/PUT/DELETE  /api/projects/{pid}
      ↓
  require_auth()      → Sessions 조회, status='active' 확인. 아니면 401
      ↓
  require_project(pid, action)
      ├─ level 3            → 허용
      ├─ level 2 && owner   → action in {read, write} 이면 허용, delete 는 거부
      ├─ level 1            → 발행된 회차의 결과물에 한해 read 만 허용
      └─ 그 외              → 403
```

**판정은 이 함수 한 곳에서만 한다.** 라우터마다 `if level >= 2` 를 흩뿌리면 반드시 빠뜨리는 곳이 생기고, 그게 곧 권한 우회 구멍이 된다.

프런트의 버튼 숨김은 UX일 뿐 방어가 아니다. 서버 가드가 없으면 API를 직접 부르는 것으로 뚫린다.

### 4.1 회귀 테스트 스위트 (W1 완료 게이트)

**4개 계정**(승인대기 · L1 · L2 · L3)으로 **모든 엔드포인트**를 자동 테스트한다.

| 엔드포인트 | pending | L1 | L2(소유) | L2(타인) | L3 |
|---|---|---|---|---|---|
| `GET /api/projects` | 403 | 발행본만 | 본인 것만 | — | 전부 |
| `GET /api/projects/{id}` | 403 | 발행본만 | 200 | 403 | 200 |
| `PUT /api/projects/{id}` | 403 | 403 | 200 | 403 | 200 |
| `DELETE /api/projects/{id}` | 403 | 403 | **403** | 403 | 200 |
| `GET /api/comments?project=` | 403 | **403** | 본인 것만 | 403 | 전부 |
| `POST /api/comments` | 403 | **403** | 본인 이북만 | 403 | 200 |
| `POST /api/cycles` | 403 | 403 | 403 | — | 200 |
| `POST /api/users/{id}/approve` | 403 | 403 | 403 | — | 200 |

굵게 표시한 칸이 특히 놓치기 쉬운 지점이다 — L2의 삭제 거부, L1의 메모 완전 차단.

## 5. 기존 데이터 이관 (W1)

현재 `Projects`에는 `owner_id`가 없다. 이관 절차:

1. **롤백 스냅샷** — `ebook_html.db` 파일을 통째로 복사해 보관. 이걸 먼저 한다.
2. 시드 L3 관리자 계정 생성
3. 기존 `Projects` 전건에 `owner_id = 시드 L3`, `cycle_id = NULL` 일괄 부여
4. `Notes` → `Comments` 이관. `author_id = 시드 L3`, `status = 'closed'`, `created_at = updated_at × 1000` (초→ms)
5. L3가 화면에서 실제 소유자에게 재배정

이관 스크립트는 **멱등**이어야 한다(두 번 돌려도 결과 동일). `owner_id IS NULL` 조건으로만 갱신한다.

## 6. 결정 이력 · 미결 사항

### 6.1 확정 (2026-08-19)

| 항목 | 결정 |
|---|---|
| 시드 L3 계정 | `login_id = admin`, 최초 로그인 시 비밀번호 강제 변경, 이후 비상용으로만 보존 |
| **배포 형태** | **사내망 사설 IP + 기존 사내 VPN.** 포트포워딩 없음, HTTP 유지, CORS 무관 (§2.2.1) |
| `ebook_html.db` 개명 | W1 이관과 동시에 `ever_sketch.db`로. 환경변수도 `EVER_SKETCH_DB`(구 `EBOOK_HTML_DB` 폴백 유지) |

> 서버 위치가 **더 이상 크리티컬 패스가 아니다.** VPN이 이미 있어 외부 접속 요구가 추가 개발 없이 해소됐고,
> HTTPS·CORS·자가가입 제한이 전부 불필요해졌다. W1 인증은 이 전제 위에서 바로 짤 수 있다.

### 6.2 미결

| # | 항목 | 결정 필요 시점 |
|---|---|---|
| 1 | 서버로 쓸 장비와 사설 IP 확정 | W2 (9/5) |
| 2 | 세션 유효기간 12시간이 적절한지 | W1 착수 전 |
| 3 | 백업 정책 (SQLite 파일 일 1회 + 보관 기간) | 10월 배포 전 |
| 4 | SQLite 동시 쓰기 한계 — 임원 10~20명 동시 편집 시 WAL 모드로 충분한지 | W5 리허설에서 실측 |

> 4번은 미리 답하기 어렵다. SQLite는 쓰기가 직렬화되므로 **동시 자동저장이 몰리면 지연이 생길 수 있다.**
> W1에서 WAL 모드(`PRAGMA journal_mode=WAL`)를 켜두고, W5 리허설에서 실제 지연을 측정한다.
> 문제가 확인되면 PostgreSQL 전환(v1.1 이월 항목)을 앞당긴다.
